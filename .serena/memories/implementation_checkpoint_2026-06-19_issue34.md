マイルストーンM1「譜面・曲プロファイルパイプライン」の最上流であり、解析先行ゲート（#96）の検査対象となる曲プロファイルJSONの契約を定める。Issue #34 は型定義と実行時バリデータのみを提供し、データ生成（#45・#46）・和音名から音高への変換（#35）・JUST音程スロット生成（#36）・無和音区間の音階埋め（#37）・ノーツ生成と配置（#38・#40）はこの契約に従う下流Issueの責務である。

## 最重要の意思決定

- **段階的検査**: 検証関数は2層を持つ。第1層は解析の必須項目（テンポ・ビート格子・コード進行・繰り返し区間・声量曲線・感情曲線・歌詞文字タイミング・歌詞密度・無和音区間・見せ場マップ）とメタ・ロード元・調を厳密に検査する。これが解析先行ゲートの「必須項目を全て備える」要件に対応する。第2層は譜面派生フィールドの存在と基本不変条件、および下流が前提とする構造対応を検査する。協和性・被覆率・歌詞密度の数値整合の妥当性は生成側（#36・#46）の責務として委譲する。ゲート要件が必須項目の充足であり、数値妥当性まで先取りすると責務が重複するからである。
- **手書きの純関数バリデータ（新規依存ゼロ）**: `validateProfile(value)` は検証ライブラリを使わず手書きとする。`docs/decisions/architecture.md` §2「先取りして依存を増やさない」と `src/config/songs.test.ts` の手書き検証の作法に倣う。例外を投げず欠落と不正の一覧（`path` と `message`）を返す。検証ゲートが1回の実行で全問題を報告できると修正が早いためである。ファイル操作・プロセス・ブラウザの文書要素に依存しないため、CIのゲート（#96、Node.jsで `.json` を読み検証関数へ渡す）とブラウザの読込時の双方から呼べる。
- **コードトーン格子（slots）は和音区間ごとのトラックで chords と1対1**: 和音は和音区間内で一定なので、和音区間ごとに1要素のトラックにすると冗長が最小になり、無和音区間の扱いも区間として自然に表現できる。境界は `chords` と一致させ、無和音でない区間は和音名を一致させる。無和音区間のスロットは解決後の和音名または調の音階を表し、無和音記号のままにはしない。
- **全データ埋め込み**: ロード元・解析の必須項目・譜面派生フィールドを1つのJSONに書き込み、実行時の再計算を無くす（`docs/research/04` §2・§4）。
- **ロード元の照合**: `source`（楽曲キー・URL・音楽地図識別子）が `src/config/songs.ts` の確定ロード設定 `SONGS` と一致することを検査する。`song.key` と `source.songKey` の一致も検査する。楽曲ロードの正典は `docs/support-page.md` であり、別バージョンや別の音楽地図から作られたプロファイルを最上流で弾くためである。
- **値域の範囲は tuning.ts を参照**: スロット数（5から9）とタップ上限比率（0.4から0.8）の範囲は `src/config/tuning.ts` の定数（`PITCH_SLOT_COUNT_MIN/MAX`・`TAP_LIMIT_RATIO_MIN/MAX`）を import して参照する。二重定義による不整合を避けるためである。曲固有の絶対値（フル434・上限260・見せ場6）はプロファイル側に置く。
- **色と操作音の表現**: 色はX軸の位置から色への対応（停止点の先頭を x=0、末尾を x=1 とし全X範囲を覆う）。操作音は通常時と投下時の2音色で、波形はWeb Audioの基本4種（sine・square・sawtooth・triangle）に限る。発音周波数はスロット音高から導出するため音色には持たせない。ひまわりと蝶の固定色と同時発音数の上限は曲非依存のためプロファイルに置かない。
- **カメラ補間の契約**: キーフレーム間はCatmull-Romスプラインで補間し、その補間を描画（#40）と判定（#48）が共有する。判定の軌跡上距離と速さは `camera` と `timeMs` から #48 が導出するため、ノーツには保存しない。判定と描画が別の補間を使うと軌跡上距離と見た目がずれるためである。

## 採用した数値とその理由（すべて理由を先に述べる）

- 連続被覆の許容誤差 = 1ミリ秒: 音楽地図の時刻は浮動小数点で末尾に微小な揺れがあり（実例 1371.6999999999998）、隣接区間の完全一致を課すと正しいデータを落とすため。1ミリ秒は16分音符の86ミリ秒・1拍の343ミリ秒よりはるかに小さく実在の隙間を見逃さない。
- 末尾の許容超過 = 2000ミリ秒: コード区間は曲長をわずかに超えて記録されることがあり（TAKEOVERでは曲長237250ミリ秒に対しコードが237269ミリ秒まで伸びる）これを許容する必要がある一方、上限が無いと数秒以上の破損を見逃すため。毎分175拍では1小節が約1372ミリ秒であり、2000ミリ秒は末尾1単位の鳴り切りを確実に含み数秒以上の明白な誤りを排除する。
- スキーマ版数 = 1に固定して検査: 互換性のゲートとして想定版数と異なるプロファイルを拒否する必要があるため。契約に破壊的変更が入ったときにこの値を増やす。

## 実装した内容（新規 `src/profiles/schema/`）

- `profileSchema.ts`: `SongProfile` と全サブ型。`SongVideo` は `src/config/songs.ts` から import して再利用。時刻はミリ秒、音高はMIDIノート番号。
- `validateProfile.ts`: 検証関数本体。`ValidationResult` と `ValidationError` 型。`src/config/tuning.ts` の範囲定数と `src/config/songs.ts` の `SONGS` を参照。
- `index.ts`: 型と検証関数の公開窓口。
- `fixtures/minimalValidProfile.ts`: 検証テスト用の小さな正しい実例（実TAKEOVERデータではない。`source` は SONGS の "takeover" 登録値に一致）。
- `validateProfile.test.ts`: 合格と各不正の不合格を固定するテスト。
- `src/profiles/README.md`: `schema/` の責務を追記。
