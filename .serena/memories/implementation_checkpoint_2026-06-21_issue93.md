## 最重要の意思決定

- **モーション層を `src/rendering/entities/` に置く**: ボーン操作は描画ドメインの関心であり、対象は中心オブジェクトのVRMに限られるため、`centerFigure` と同じ階層に置いて所有関係を明瞭にする。`centerFigure` がモーション層を所有し、毎フレーム駆動する。
- **抽象は最小の2操作に絞る**: 毎フレーム更新 `update(deltaSeconds)` と後始末 `dispose()` だけを持つ。固定ポーズ・手続き的・再生型のいずれも「毎フレーム何かを進める」と「終了時に資源を解放する」で過不足なく表現でき、操作を増やすと固定ポーズの実装に無用の空実装が生じるためである。
- **最小実用版は固定ポーズ（無動作）**: `createFixedPoseMotion` の `update` は何もしない。読み込んだVRMの既定姿勢（両腕を真横に伸ばしたバインドポーズ）を毎フレーム変えない。これが仕様7節の「ポーズを固定し、モーションを与えない実装」に対応する。立ち姿の見栄え付与（バインドポーズからの自然な待機姿勢）は本Issueの範囲外であり、後続の手続き的モーションが担う。Issue #64 のチェックポイントが #93 へ期待した姿勢変更のうち、本Issueは抽象層と差し替え口の確立までを担い、姿勢変更そのものは後続へ送る。
- **差し替え口は同期の生成関数を受ける**: `setMotion(create: (loaded: LoadedVrm) => VrmMotion)`。`centerFigure` がVRM本体の外部公開を避けたまま、後続のボーン操作（`vrm.humanoid`）にも再生型（`vrm.scene` への `AnimationMixer`）にも必要な対象を生成関数へ渡せるためである。再生型が必要とするVRM Animation素材の非同期読み込みは差し替え口の外側で先に済ませ、同期的に組み立てた `VrmMotion` を渡す方針とする。`centerFigure` と差し替え口を同期処理に保ち、描画の層へ非同期や時刻の関心を持ち込まないためである。
- **更新順序はモーション更新を `vrm.update` の前に行う**: 姿勢入力（手続き的なボーン回転、または再生制御による姿勢入力）を先に適用し、その後の `vrm.update` がVRM内部の更新（姿勢の反映・ばねの揺れ・表情）を進める順にすると、当フレームの姿勢入力が同じフレームのVRM内部更新へ取り込まれるためである。
- **後始末系は例外を投げない契約**: モーション層の `dispose`、`centerFigure` の内部解放手続きと光柱解放、既存の `LoadedVrm.dispose` は例外を投げない。既存実装が後始末済みを表す真偽値で冪等化され内部で例外を投げない実装であり整合する。この契約により、差し替えと後始末で例外を投げうるのは差し替え口 `setMotion` の生成関数のみとなり、例外の伝播方針が1か所に統一される。本Issueの新規コードは外部ライブラリの後始末を新たに呼ばないため契約は自明に成立する。外部資源を持つ後続の再生型モーションは、実装時に外部呼び出しを例外を捕捉して外へ出さない形で囲む方針をコメントへ前もって記した。
- **解放順序と参照の先行切り離し**: 後始末と再差し替えは「モーション解放 → VRMをシーンから除去 → VRM解放」の順で行い、解放前に内部参照（`motion`・`loadedVrm`）を局所変数へ退避して null を代入する。後続の再生型モーションはVRMのシーンや再生制御を参照するため、VRMのシーンを先に解放するとモーションが解放済みの対象を参照しうるためである。あわせて、解放の途中で例外が生じても内部状態が解放済みの古い資源を指したまま残らないようにするためである。
- **差し替え時は新VRMを取り込んでから旧資源を解放**: 差し替えの間に中心表示が一瞬も空にならないようにするためである。差し替えは別インスタンスのVRMを前提とする。`renderRoot.mountCenterCharacter` は呼ばれるたびに新しい `LoadedVrm` を生成するため、同一インスタンスが再投入される経路が存在しないためである。

- `src/rendering/entities/centerFigure.ts`（変更・テスト追加）: モーション層 `motion` を所有。`CenterFigure` の契約へ `setMotion(create: VrmMotionFactory)` を追加。旧VRMと旧モーションの解放を1か所へ集約する内部手続きを追加。`update` の読み込み済みVRM分岐で `motion?.update(deltaSeconds)` を `loadedVrm.update(deltaSeconds)` の前に呼ぶ。`swapToVrm` を「後始末ガード維持 → 新VRMの配置とシーン追加 → 旧資源解放 → 光柱解放 → 状態確定と既定固定ポーズ設定」に並べ替え。`setMotion` は後始末済みとVRM未読み込みで早期に何もしない。それ以外は新モーションを先に生成し、生成成功後に直前のモーションを解放して置き換える（生成が例外を投げた場合は直前のモーションを保持して例外を呼び出し元へ伝播する）。`dispose` を解放集約手続きへまとめる。
- `src/rendering/README.md`（変更）: モーション層を内部拡張点として記録。後始末は例外を捕捉して外へ出さない契約であること、後続の手続き的・再生型モーションの差し込み先であることを記す。

## 採用した判断とその理由（すべて理由を先に述べる）

- 毎フレーム更新の引数名を `deltaSeconds`（前フレームからの経過秒の差分。絶対時刻ではない）に統一する: 再生型モーションが使う `THREE.AnimationMixer` の更新が差分秒を前提とし、描画の層が時刻の論理を持たない制約（`docs/decisions/architecture.md` §5）と整合するためである。本Issueは新しい数値定数を導入しない（固定ポーズが無動作のため）。
- 差し替え口を `RenderRoot` の公開契約へ中継しない: 差し替えを呼ぶ利用側がまだ存在しないため、用途のない公開接点を先取りで広げないためである。受入条件は `centerFigure` 内部の口で満たされる。
- @pixiv/three-vrm-animation を本Issueでは導入しない: 最小実用版は固定ポーズで不要であり、未使用の依存を増やすと配信容量が増えるためである（`docs/research/06` の容量方針）。
