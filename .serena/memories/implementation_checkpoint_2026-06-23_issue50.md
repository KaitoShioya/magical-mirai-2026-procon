## ゴールと達成基準
入力の遅れ（音声出力の遅れ、入力検出の遅れ、利用者の知覚の差）を判定窓の中心移動で吸収する補正値を、利用者ごとに測って端末内（localStorage）へ保存し、次回起動時に読み出せるようにする。Issue #50 の受け入れ基準は「較正後に点滅が一致と感じる精度」。較正方式の正典は `docs/research/04-ux-and-chart-design.md` §1「較正の方法」であり、4回のタップによる測定と手動の調整つまみを組み合わせ、核は「点滅の視覚的な一致を利用者がその場で確かめながら合わせる」ことにある。判定の受け口 `JudgeOptions.calibrationOffsetMs`（既定0、符号は正が「入力が一貫して遅れる量」）は #48 で実装済みであり、本Issueは補正値の測定・保存・読み出しと較正の利用者インターフェースを担う。

達成基準を検証可能な形に具体化した内容: (1)較正を開くと現在の保存値が表示され初期つまみ位置が決まる、(2)助走の後に4回タップするとつまみに推定値が入る、(3)つまみで手動微調整できる、(4)確認段階で補正後のずれが偏差メーターへ即時表示され前後40ミリ秒以内で一致の合図が出る、(5)保存後に再読み込みしても値が残る、(6)推定が純関数の単体テストで確定値と一致する、(7)保存と読み出しが localStorage 不在・破損・範囲外でも例外を投げず既定値へ倒れる、(8)採用0件で破棄してやり直す、(9)新しい画面状態を増やさず題名画面の常設トグルで成立する、(10)タップごとに `event.timeStamp` とハンドラ内 `performance.now()` の差が600ミリ秒超なら原点不一致で破棄しやり直す、(11)つまみ値は常に推定値（参考）と明示し採用3件未満で不安定の注意を出す。

## 実装方式（採用理由を先に述べる）
判定への結線まで踏み込まず保存と読み出しの公開窓口で止める。理由は、`judgeTap` を呼ぶ生きたゲームループは #59（未実装）が所有し、#50 が結線まで踏み込むと所有が割れるため。#50 は読み出し関数 `loadCalibrationOffsetMs` を提供し、#59 がプレイ開始時に1回呼んで渡す契約にする。

依存規則（`docs/decisions/architecture.md` §3・§5）を厳守する。補正値の推定は副作用のない数値計算のため `src/utils/` の純関数に置き、特定のサブシステムや設定を取り込まず引数だけに依存する。補正値の永続化は判定に渡る scoring ドメインの値であり scoring README が localStorage の自己最高記録を scoring の責務と既定しているため `src/scoring/` に置き、調整範囲のクランプに `src/config/tuning` を読む（scoring が tuning を読む前例は `defaultWindows.ts`）。利用者インターフェースは app 統括層に置き、副作用や状態を持つ音エンジンと端末内保存は差し替えと検査を容易にするため引数注入で受け取り、純関数の推定器と定数だけを直接取り込む。

## 主要な設計判断（採用理由を先に述べる。Codex とサブエージェントの複数回の独立レビューで確定）
- 補正値の符号は正を「入力が一貫して遅れる量」とする。既存の判定式 `centeredDiff = tapMusicTimeMs - noteMusicTimeMs - calibrationOffsetMs`（`src/scoring/timingAccuracy.ts`）で差し引くと判定窓の中心が遅れ側へ動くため。推定器は中央値を符号反転せずに返す。
- 中央値を採る。4タップ程度では1回から2回が大きく外れることがあり、平均は外れ値1つで大きくぶれるが中央値は半数が正常なら頑健なため。
- 各タップを最も近い点滅へ対応付け、点滅ごとに最も近い1タップへ集約する。順番対応は途中の点滅を1回見逃すと以後の対応が全部ずれるが、最近傍なら見逃しに強く、点滅ごとの集約は二度押しの歪みを防ぐため。
- 外れ値の閾値を200ミリ秒とする。点滅の周期600ミリ秒では最近傍の点滅との差が構造上前後300ミリ秒に収まり、200ミリ秒は周期の約3分の1かつ判定の外端90ミリ秒の2倍より広く、これを超えて離れたタップはその点滅を狙っていないとみなせるため。原点が一定量ずれて全タップが大きく外れた場合も、この閾値で全タップが落ちて採用0となりやり直しへ倒れる。
- 点滅の周期を600ミリ秒（毎分100拍相当）とする。較正で測る遅れは端末と人間の特性で曲に依らず、やや遅めの一定間隔の方が拍を予測して正確に合わせやすいため。曲固有の1拍343ミリ秒は速すぎてタップ誤差が増える。
- 補正値の調整範囲を下限マイナス150・上限プラス200ミリ秒と非対称にする。入力検出の遅れと音声出力の遅れがともに遅れ側へ偏り、無線接続の音声出力の遅延が100から200ミリ秒に達するため正方向を広く取る。満点窓の前後40ミリ秒・外端の前後90ミリ秒を十分に包む。
- つまみの刻みを5ミリ秒とする。満点窓の前後40ミリ秒に対し5ミリ秒刻みなら窓内に16段階あり、つまみで体感的に合わせるのに十分細かいため。
- 一致の合図の窓を前後40ミリ秒とする。満点窓の前後40ミリ秒に合わせ、本番の満点と同じずれ幅で一致を感じられるようにするため。
- 音声出力の遅れ `outputLatencyMs` は `(context.outputLatency + context.baseLatency) * 1000` で算出する。両者は秒で報告され作品全体の時刻をミリ秒で統一しているため1000倍する。未対応のブラウザの undefined は0に倒す。AudioContext が起動していなければ null（推定不能）。この値は初期つまみ位置の参考値としてのみ提示し、最終補正値へは自動採用しない。出力の遅れは入力の遅れを含まないため。
- 時刻原点の一致を確かめる差の上限を600ミリ秒とする。`pointerdown` のハンドラは入力イベントと同じ描画フレーム内で実行されるため `event.timeStamp` とハンドラ内 `performance.now()` の真の差は1点滅周期より十分小さく、これを超える差は両時刻が別の原点であることを直接示すため。点滅の実表示時刻を `performance.now()`、タップを `event.timeStamp` で記録して同一原点で揃える前提は、既存実装 `src/scoring/tapMusicTime.ts` の注釈「event.timeStamp とフレームの実時計（performance.now が渡す時刻）は同じ高精度時刻基準」に依拠する。
- 信頼できる最小の採用サンプル数を3とする。4個の中央値は3件以上が正常なときだけ頑健で、2件以下では信頼できないため、採用が2件以下のときは不安定の注意を出す。
- 助走を4拍とする。4分の4拍子の1小節にあたる慣例的な予備拍で、周期600ミリ秒のテンポに乗るのに十分なため。
- 目安欄（音声出力の遅れの目安と「目安をつまみに入れる」ボタン）は待機と確認の段階に限って表示する。目安はつまみの参考値であり、タップでリズムを測る助走・測定の間はつまみを触らないため隠して操作を紛らわしくしないため。
