# 全体決定事項（アプリケーション仕様・設計の確定版）

この文書は、マジカルミライ2026プログラミングコンテスト応募作品の設計判断を確定形で記す。各判断は「採用した理由」を先に述べ、その後に「決定内容」を書く。調査の詳細な根拠は `docs/research/` の各文書を参照する。規約の正典は `docs/concept.md`、楽曲ロードの正典は `docs/support-page.md`、作品コンセプトの正典は `docs/idea/concept-final.md`。

## 1. 用語定義

本作で使う固有の用語を定義する。以降の記述はこの定義に従う。

| 用語 | 定義 |
|---|---|
| ハメ | プレイヤーが楽曲のタイミングに合わせて画面をタップし、音と映像が一致して気持ちよさが生じる操作。 |
| タップの3次元入力 | 1回のタップが持つ3つの値。タイミング（いつ叩くか）、Y軸の値（音程）、X軸の値（エフェクトの色）。 |
| コードトーン格子 | その瞬間の和音を構成する音を、画面のY軸（縦方向）の位置に割り当てた対応表。どのY位置を叩いても和音の構成音が鳴る。 |
| JUST | 楽曲がその瞬間に最もふさわしいとする正解の値。タイミングのJUSTと音程のJUSTがある。JUSTに近いほど高い得点になる。 |
| 失敗のない床 | どのタップも必ず和音を生み、楽曲終了後に必ず光点を生む設計。判定が外れても演出は破綻せず、得点と光点の豊かさの差だけが生じる。 |
| 見せ場 | 楽曲の盛り上がる区間。声量と歌詞密度の解析で抽出する。TAKEOVERでは6箇所。 |
| ゲージ | タップの成功で蓄積する量。見せ場で消費して演出を強める。 |
| 投下 | 見せ場でゲージを消費し、ノーツ効果音の音色を変えて得点の倍率を上げる操作。 |
| ポートフォリオ | 限られたタップ回数とゲージを、どの見せ場に配分するかという戦略。 |
| 多様性逓減 | 楽曲のJUSTが変化したのに同じ操作を繰り返した場合に、得点を減らす仕組み。 |
| 一回性 | 1回のプレイでは全ての要素を取り切れないこと。タップの総数に上限を設けて成立させる。 |
| 2チャンネル原則 | プレイヤーが操作中に意識するのは「ハメ」と「投下の判断」の2つだけにする方針。多様性逓減と一回性はプレイ後に開示する。 |
| 体験の3層 | 観るだけで楽しい層、遊ぶと気持ちよい層、構造を理解して深める層の3段階。 |
| ランク | プレイ結果を4段階で表す評価。低い順にC、B、A、S。 |
| 成果物 | プレイ後に生成する深夜の湖の静止画。湖面のひまわりと蝶の灯しと、本編開始から湖の中心に常在する初音ミクが並ぶ。得点とランクを統合して撮影する。 |
| ウォームアップ | 楽曲再生の前に置く準備区間。 |
| 3空間分離 | 入力の判定面（動かない2次元）、演出のカメラ空間（動く3次元）、画面四隅の操作情報（動かない）の3つを分け、座標の変換を入力から演出への一方向だけに限る設計。 |

## 2. 作品コンセプト要約

マジカルミライ2026のテーマ「湖のソナーレ」を舞台に、疾走するキネティックタイポグラフィ（文字そのものを動かす映像表現）と「ハメ」で湖を奏でるリリック・リズム作品である。

体験の3層は次の保証を持つ。

| 層 | 保証する内容 |
|---|---|
| 観るだけで楽しい | 操作をしなくても完成した演出が流れる。タップを温存することも戦略であり、観ることが劣位にならない。 |
| 遊ぶと気持ちよい | タップは必ず和音を生む。判定の差は得点と楽曲終了後の光点の豊かさにだけ表れる。 |
| 構造を理解して深める | 反射神経ではなく、構造の理解で得点が伸びる。 |

目的関数は次の3つの積で表す。ポートフォリオ（配分の戦略）、多様性逓減（変化と反復の読み）、一回性（取り切れなさ）である。操作中はハメと投下の判断だけを意識し、多様性逓減と一回性はプレイ後に結果として開示する。

楽曲は縦切り方式で進める。最初の1曲をTAKEOVER（Twinfield）とし、共通エンジンと曲ごとのプロファイルを分離して実装する。共通エンジンは体験の3層、コードトーン格子、目的関数、得点とランクを担う。曲プロファイルは効果音、カメラ軌跡、灯しのパターン、JUSTのパターン、見せ場マップを担う。

舞台は深夜・雨の湖の3次元空間である。カメラが歌詞空間を移動して立体的に歌詞を見せ、その軌跡が、楽曲終了後に湖面へ灯す光（ひまわりと蝶）の配置を決める。設計の最新の正典は `docs/idea/concept-final.md` であり、本文書はその設計判断と採用理由を記す。

## 3. 確定した設計判断

### 3.1 操作環境

**採用理由**：スマートフォンの利用者は片手の親指1本だけで操作する場面が多いが、本作のタップは音程（Y軸）と色（X軸）を画面上の位置で選ぶため、画面を広く使える持ち方が有利である。横持ちの両手操作は画面を広く使え、両手で和音的な同時タップができる。

**決定**：スマートフォンの横持ち・両手操作を主軸とし、パソコンにも対応する。

### 3.2 描画ライブラリの構成

**採用理由**：疾走感の演出として、3次元空間に置いた文字の間をカメラが移動する表現を中心に据える。これには真の透視投影カメラ（遠近を表現するカメラ）が必要で、2次元描画ライブラリのPixiJSでは実現できない。1つのWebページで複数のWebGL（ブラウザでGPU描画を行う仕組み）の描画領域を重ねると、スマートフォンでは描画領域の数の上限（Chromeで実質8、Firefoxのモバイル版で2）に達して描画が壊れるため、描画は1つの領域に統一する必要がある。three.jsは3次元描画と2次元描画の両方を1つの領域で扱える。

**決定**：描画ライブラリをthree.jsに統一する。湖面の反射はシェーダ（GPUで画素ごとの色を計算するプログラム）と平面反射で描き、発光する灯しはブルーム後処理でにじませ、音符はInstancedMesh（同じ形を1回の描画命令で多数並べる仕組み）で描き、3次元の文字はtroika-three-text（フォントを読み込んで3次元空間に文字を描くライブラリ）で描き、ミクはVRoidで自作したVRMモデルを@pixiv/three-vrmで読み込み、成果物の画像はRenderTarget（描画結果を画像として取り出す領域）から取り出す。読ませるための歌詞は、ブラウザの文書要素（HTMLのDOM）にGSAP（アニメーションを制御するライブラリ）を組み合わせて最前面に重ねる。プログラミング言語はTypeScriptを使い、画面の枠組みを作るためのフレームワークは使わない。

### 3.3 入力アーキテクチャ（3空間分離）

**採用理由**：演出のカメラが3次元空間で移動しても、操作の判定が破綻してはならない。3次元の物体との交差判定で入力を取ると、カメラの移動に伴って判定面が動き、また「外す」という概念が生じて失敗のない床に反する。Cytus、Arcaea、Phigrosといった視点が動くリズムゲームは、判定を視覚のカメラから切り離し、画面座標で判定している。

**決定**：入力の判定面（動かない2次元）、演出のカメラ空間（動く3次元）、画面四隅の操作情報（動かない）の3つを分離する。座標の変換は入力から演出への一方向だけに限り、3次元から入力への逆変換は行わない。タップの判定は画面座標を直接ゾーンに分けて行い、カメラの行列を参照しない。X軸の位置を色に、Y軸の位置を音程に、純粋な関数で写像する。複数の指の同時操作はPointer Events（マウスとペンと指を同じ仕組みで扱うブラウザの入力イベント）で受け、各接触に割り当てられる識別番号で独立に管理する。タイミングは、カメラの軌跡上のノーツ点と、反応した瞬間の軌跡上の点との、軌跡に沿った距離で定義する。判定窓は時間で定め、各ノーツ点でカメラの軌跡上の速さを掛けて距離へ翻訳することで、カメラの速い区間でも遅い区間でも同じ時間の許容で公平に保つ。判定の合図は画面右下の落下式のレーン（目標線と落下するノーツ点と音程の番号1から7）で与え、本編画面の左端にY軸の1から7の境界を薄く表示する。

### 3.4 スコアリング数式

**採用理由**：目的関数を3つの積として定義したため、得点もタップ1回ごとに精度と多様性逓減と投下の積を取り、それを合算する形にすると、3つの要素が自然に相互に依存する。タップ総数に上限があることが一回性を表す。コンボの倍率は、持続的に操作することへの加算的なご褒美であり、難易度による飽きとの結びつきが薄いため導入する。ただし反射神経への依存を避けるため、上限を設けて全体の得点に占める割合を十数パーセント以内に抑える。

**決定**：タップ1回の得点を次の式で表す。

- タップ素点 `a` ＝ タイミング強度 × 重み ＋ 音程強度 × 重み（X軸の色は得点に寄与しない。両方がJUSTのとき最大）
- 多様性係数 `D`：通常は1.0。JUSTが変化したのに前と同じ操作を繰り返した場合だけ1.0未満になる
- 投下倍率 `M`：見せ場で投下したとき、消費したゲージの割合と見せ場の重みに応じて1.0より大きくなる
- コンボ加点 `combo`：連続して精度の高いタップが続くほど増える加算値。上限を持つ
- タップ1回の得点 ＝ `a × D × M ＋ combo`
- 総合得点 `S` ＝ 各タップの得点の合計（タップ総数は上限を持つ）
- ランク ＝ 総合得点を内蔵の水準分布で百分位に変換し、C、B、A、Sの4段階に対応づける

コンボは精度の低いタップで途切れるが、タップしないこと自体は減点しない。これにより観るだけの層とタップを温存する戦略を妨げない。

### 3.5 多様性逓減のJUST進化（三部形式）

**採用理由**：失敗のない床では正誤の緊張がないため、情動を生む唯一の仕組みが「反復による記憶」と「変化による発展」の緊張になる。完全に固定すると単調になり、完全に自由にすると記憶の手がかりを失う。主題を提示し、展開し、回帰させる三部形式は、反復と変化の両方を満たし、終盤に最大の発展を置く一回性とも整合する。TAKEOVERは24秒地点と189秒地点に同じ「Clap to the Beat」が対の構造で現れる。

**決定**：JUSTを進化させる。24秒地点の最初のClap区間で主題となる正解を提示し、中盤の見せ場で変奏し、189秒地点の最終区間で主題を回帰させつつ最大の発展形を提示する。JUSTが変化した区間で前と同じ操作を繰り返した場合に多様性逓減を発火させる。進化の刻みは楽曲の反復区間の情報に同期させる。

### 3.6 ゲージと投下

**採用理由**：満タンのゲージで意味のある投下が成立し、かつ全6箇所の見せ場では取り切れない配分にするため、想定タップ数と見せ場数から逆算する。

**決定**：タップの成功でゲージを蓄積する。タイミングと音程のどちらか一方が成功したとき基本量を、両方がJUSTのときより多くを蓄積する。満タンのゲージはおよそ50タップで貯まり、これは投下5回ぶんに相当する。見せ場で投下するとノーツ効果音の音色が変わり、消費したゲージの割合と見せ場の重みに応じて得点の倍率が上がる。189秒地点の見せ場の重みを最大にする。この投下ゲージは、ランクを表す専用ゲージとは別物である。

### 3.7 一回性（タップ総数上限）

**採用理由**：全6箇所の見せ場をすべて最適に投下することができない密度にすると、どこに配分するかの戦略が生じ、別の配分を試す動機が生まれる。

**決定**：1回のプレイで使えるタップの総数に上限を設ける。上限はフルに可能なタップ数のおよそ6割を目安とする。具体値は実装後のプレイ検証で調整する。

### 3.8 ウォームアップ

**採用理由**：TAKEOVERは0秒から演奏が始まり、楽曲の中に無音の導入部分がない。準備の時間は楽曲再生の前に独立した区間として作る必要がある。操作の習得は失敗のない床に委ねられるため、練習や説明の特別な仕掛けは不要である。

**決定**：ウォームアップは固定の長さで自動的に進む最小構成とする。題名から湖面がゆっくり現れる導入演出を見せ、最後の3秒に3、2、1のカウントダウンを表示し、カウントに合わせて楽曲本編へ移る。ビートの予告、自由な練習、操作の説明、クラップの誘導は入れない。ウォームアップ中にタップした場合も本編と同じ和音と波紋を返す。観るだけの層は固定の長さの後、自動的に本編へ進む。画面の遷移は、題名画面、ウォームアップ、プレイ、結果、再挑戦の5状態を自前の状態管理で扱う。

### 3.9 灯しの造形

**採用理由**：ひまわりはキービジュアルの中心であり、黄金角（約137.5度）に基づくフェルマー螺旋の数式で形を生成できるため、コードによる描画が容易で軽量である。固定色の発光造形にすると、配置がランダムでも、反応が0でも部分でも最大でも自然に美しい湖面の灯しになる。

**決定**：ひまわりは各ノーツ点の真下に置くオレンジ色に光る造形、蝶は空間上のノーツ点に置くネオンブルーに光る造形とし、楽曲終了後に湖面へ配置する。反応強度の写像は、タイミング精度を大きさ、音程精度を輝度に対応させる。色は固定のため得点に寄与しない。蝶は演奏中はハメた瞬間に舞って消えるノーツ効果として使う。白鳥は後の拡張とする。楽曲終了後の配置は、カメラ由来の素案位置にボロノイ緩和を少数回かけ、自然なゆらぎを残しつつ不自然な空白と硬い塊を除く。

### 3.10 ランクの専用ゲージ

**採用理由**：場面の色を深夜の湖とオレンジとネオンブルーの灯しで固定するため、ランクを場面全体の色彩変化で表すと世界観と衝突する。ランクを専用のゲージで表すと、場面の色を固定したままスコアの伸びを連続的に見せられる。色の補間は、明度と彩度が色相によって不均一になる従来のHSL表色系を避け、知覚的に均等なOKLCH表色系（明度・彩度・色相を知覚に沿って表す色空間）で行う。

**決定**：ランク4段階は専用ゲージで表す。スコアの増加でゲージが蓄積し、ゲージの色彩が4段階（C、B、A、S）で連続的に変化する。ランクゲージは投下ゲージとは別物で、判定レーンの上に表示する。スコアとランクは撮影時にゲージの表示へ統合する。旧仕様の寒色から暖色へのランク色彩アークと、湖の満ち方のグラデーションは廃止する。

## 4. 規約ガードレール要点

実装と提出で必ず守る制約を記す。詳細は `docs/concept.md` を参照する。

- **静的なWebアプリケーションに限る**。サーバ側で動的な応答を返すプログラムと、自前のバックエンドのAPIは作らない。ランキングは、開発者が用意した水準分布を静的なデータとして同梱して百分位を表示する方法と、ブラウザのローカルストレージに自己最高記録を保存する方法と、成果物の画像を共有する方法で実現する。
- **表示する絵・音楽・文章にAIが生成した素材を使わない**。判断の境界は「素材をAIが生成したかどうか」である。AIが完成品として作った画像・SVG・イラスト・音源・3次元モデルをプログラムに組み込んで表示することはできない。コードによる動的な描画と、コードの作成へのAIの支援は認められる。形の元データ（頂点の座標や輪郭の点）は人間または数式が作り、AIには描画の処理だけを書かせる。設計検討用に作ったSVGの見本（`docs/img/` の配色見本と `play-screen-layers.svg`）は設計資料に限り、アプリには組み込まない。
- **キャラクターはピアプロキャラクターズの6名に限る**（初音ミク、鏡音リン、鏡音レン、巡音ルカ、MEIKO、KAITO）。ミクはVRoid Studioで人間が二次創作モデルを自作し、VRM形式で書き出して@pixiv/three-vrmで読み込み、コードで動的に描画する。人間が制作したモデルのためAI生成アセットの禁止に抵触しない。営利化しない無償の応募作品のためピアプロ・キャラクター・ライセンスの条件を満たす。指定文言とクリプトンのキャラクター利用のガイドラインに従う旨をアプリ内に常に表示する。公式のWebサイトとSNSに載っているイラストとロゴは転用しない。
- **効果音は操作のフィードバックとして鳴らす**。自作または正規に利用許諾を得た素材を使い、楽曲の一部と誤解されない音色と音量にし、消す設定を用意する。
- **静的な素材は人間の自作または権利が明確な素材に限り、作者名をアプリ内に表示する**。
- **提出はGitHubの非公開リポジトリで行い、応募フォームに動作環境を明記する**。READMEにビルドと実行の手順を書く。ソースコードの難読化は行わない。
- **締切は2026年6月29日（月）正午（日本標準時）**。締切から入賞発表までの間は、プログラムと付随するアセットを一切更新しない。
- **アプリトークンと`.env`ファイルはコミットしない**。

## 5. 残る作業

主要な設計判断はすべて確定した。残るのは深掘り調査と実装による検証である。最初の検証は、three.jsとtroika-three-textで縦切りの最小スライスを作り、深夜・雨・湖面の平面反射・発光ブルーム、キネティックタイポグラフィ、3次元のカメラ移動、2次元の入力グリッド、音程付きの操作音をTAKEOVERで動かし、スマートフォンで毎秒60フレームを維持できるか、操作から発音までの体感の遅れが許容できるかを実測することである。あわせて、参考映像の解析によるキネティックタイポグラフィの文法の確定、楽曲解析によるノーツの自動生成、ミクの自作モデルの用意を行う。具体的な数値（判定窓、Y軸スロット数、タップ総数上限、ゲージの数値）は、`docs/research/07-feasibility-and-parameters.md` の見積もり値を初期値として実装後のプレイ検証で調整する。復帰点は `.serena/memories/concept_revision_checkpoint_2026-06-14.md` である。
