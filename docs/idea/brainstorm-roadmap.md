## 進行ルール（ユーザー指示の遵守事項）

1. 方針決定・アイデア出し・楽曲選定（1曲/複数/全曲）・コンセプト練り上げの**主体はユーザー**。Claudeはユーザーの意見を取り込みながら整理・言語化・素材提示を行う
2. Claudeは回答を要求して意思決定を迫らない（強制選択肢で進路を縛らない）。問いは自由回答の招待であり、ユーザーは答えたいものだけ答えてよい
3. **ロードマップ型**: ユーザーの回答を反映 → 次の回答までのステップを進める。ステップの戻り・スキップ・並走は自由
4. アイデアは全部まとめ上げなくてよい。見通しが悪いものは棄却OK、ただし棄却の際もユーザーと議論を欠かさない
5. 全体フロー: ①コンセプト/構成/UXブレスト（じっくり）→ ②技術調査（技術要素・リリック表現技術）→ ③プロコンルール照合で実現構成・UX妥協点 → ④アプリ設計

## ユーザーの作品イメージ（ブレストの出発点・原典）

1. **疾走感のある流れるような表現**を軸に置く
2. **やりこみ要素**: 表現にユーザーを巻き込み、上手く操作する程気持ち良い表現になる。形態は (a)静的な表現構成作成と完成後演出の分離型 (b)ゲーム的に演出と操作が同時進行する型、どちらでもOK
3. **テキスト表現**: docs/idea/DXW0aT6FKSlkqBq2.mp4 のようなビート/リリック同期の表現力の高いテキスト表現。【STEP 5 で精緻化】区間ごとにテキスト/非テキストをスイッチするのではなく、**テキスト表現とそれ以外（映像構成技術・権利OK素材）を同時・適材適所に重ねて全体を構成**する。テキストならではの持ち味は最大限活用し、**互いの表現を阻害しない**ことが設計要件
4. **付加的な音楽表現**: 曲のインスト（ドラム音などのビート）を曲全体で整合性のある形で付加する音楽表現＋それに合わせたエフェクト/オブジェクト変化。**発想レベルであり必ず使うとは限らない**。踏み込むなら「楽曲の演出としての整合性＋音楽として表現する意味」を持つ形を模索。見通しが悪ければ棄却
5. **素材方針**: AI生成の絵/動画は使えない（規約）。権利的に利用可能な素材（ニコニコモンズ・効果音ラボ等の規約OK素材）、ピクトグラム的イラスト、トレースが容易な一般的オブジェクトは使うべきものを使う。**映像構成技術・編集技術の工夫により、少ない素材（ユーザーがクリエイターではないハンデ）で効果的に表現する**
6. **報酬設計**: 楽曲の性質によって重心を全く別に設計する
7. **操作環境**: スマホ主軸+PC対応の想定はあるが、詳細はコンセプト・全体構成・UXの軸が固まってから決める
8. **表面的な造形にも素材方針を持って挑む**（STEP 2 で追加）: 核の本質（疾走感・ハメ・テキスト表現）だけでは作品の表面的な造詣が失われがち。歌詞の解釈的な表現・MV的な映像世界・**初音ミクという存在そのものの表現**にも、素材方針（権利OK素材・ピクトグラム・映像構成技術）で取り組む

### STEP 3 続き: ハック設計の原則と目的関数（2026-06-13）— ユーザー発言

**Q. ハック対象の組み合わせ → 設計原則で回答**
- 「ついていけなくなって飽きる」ようなパラメータ（速度・反射依存が過剰なもの）は組み合わせ対象に入れない
- **出力が一方向的（単調）なパラメータも入れない**（上げれば上がるだけ＝最適解が自明＝ハック性がない）
- これにより気持ちよさとやりこみの独立性が保てる

**Q. 「まだ奥がある」の作り方**
- **自分のハックが相手に筒抜けになると興ざめする**（解法の公開は逆効果。幽霊再生・リプレイ共有系は要注意）
- **自分より腕前の高い/低い相手の存在を認識できる形**にはしたい（水準は見える、解法は見えない）

**Q. 他者参照**
- 狙撃ゲームの楽しさもオンラインが本体。オフラインだと大きく減少する。理由＝**「ハックした自分の腕前」を他者に共有したい承認欲求**が満たされないから
- 同じ構造で**他者という外部参照をユーザーに意識させる設計**にする。最も単純な例＝**スコアによるランキング**

**【ユーザーの結論】パラメータに対する出力（目的関数）をどう設計しどう具体化するかが、最も難しく最も重要な課題**

**目的関数が満たすべき制約（ユーザー発言からの整理）**
1. 非単調・組み合わせ依存（最適解が自明でない＝ハックの余地）
2. 反射神経・速度に過度依存しない（ついていけない人を作らない）
3. スコア（水準）は他者と比較可能、解法は筒抜けにならない
4. 快感（層2）はスコアと独立に常時保証
5. ハメ時のフィードバックは曲の個性（表面的造形）を纏う
6. 他者参照（ランキング等）が承認欲求の受け皿になる

### STEP 3 続き2: 目的関数の合成数とランキング・共有単位（2026-06-13）— ユーザー発言

**Q. ハックしたいファミリーと合成**
- **目的関数の複雑度（合成数）とハメ回数（時系列的複雑度=気持ちよさ）は、人間の物理的操作限界に対するトレードオフ**
- 気持ちよさを損なわない（ハメ回数を確保。疾走感と比例すべき？）形で**最適ポイントを基に合成数を決定する**（→ファシリテーターに分析依頼）
- 複雑度の直感的階段: ポートフォリオ×多様性逓減×一回性（最複雑）> ポートフォリオ×一回性（中間）> ポートフォリオ or 一回性 単体（最単純）

**Q. 承認欲求の共有単位**
- 数値スコア＋称号/ランクのみ → 音ゲーの二番煎じ感
- 数値スコア＋成果物 → 相対的位置が見えない
- **結論: 共有単位＝数値スコア＋ランク。成果物は表面的造形として出力**（共有単位とは別レイヤー）。数値スコアは目的関数の出力なので必須

**Q. ランキング階段**
- **4段目（外部APIによる本物のランキング）まで狙う**。3（シェア画像）では粒度が粗く、5以上は無駄に複雑

**Q. STEP 4 の進め方**
- ここまで特定楽曲に依存せずに要件を構造化できている → **同じ枠組みで3曲に対応できると感じるため、3曲対応で進めたい**（ファシリテーターの意見も求めつつ）
- 目的関数の抽象設計は**最適ポイントを決めてから**進める

**【ファシリテーター分析】複雑度×ハメ回数トレードオフの最適点案（2チャンネル原則）— ユーザー反応待ち**
- 鍵: 「目的関数の合成数」と「操作中に意識すべき判断の数」は独立にできる
  - 多様性逓減 → 自動計算でスコアに乗るだけ（操作中の追跡不要。リザルトで開示→次プレイの戦略変更を誘発＝ハックは**プレイ間**で起きる）
  - 一回性 → レベルデザイン側の性質（全部は取れない配置）。操作中の追加判断なし
  - ポートフォリオ → 唯一のリアルタイム判断（投下のいつ/どこ）だが低頻度
- 提案: 操作中の意識を**「ハメ（高頻度・低思考）」＋「投下判断（低頻度・高思考）」の2チャンネルに制限**。体感複雑度=中間（ポートフォリオ×一回性相当）のまま、目的関数=最複雑（3合成）を実現
- ハメ回数の目安（疾走感比例）: 平均タップ間隔500〜700ms帯を維持。シャッター=全拍(522ms)、世界最後=全拍〜2/3(400ms)、TAKEOVER=1/2拍(686ms)+サビ短時間の倍速バースト。静かなパートはチャージ/投下判断に切替（手持ち無沙汰対策と整合）

**【ファシリテーター意見】3曲対応について — 賛成（決定はユーザー）**
- 根拠: 要件が既にエンジン（3層構造・目的関数・共有単位）とプロファイル（曲別フィードバック言語・見せ場マップ・ハメレート）に分離可能な構造。曲の個性はプロファイル側で出せる
- ヘッジ提案: **縦切り先行** — エンジン＋1曲を完全成立させてから横展開（1曲でも作品成立、3曲で完成形）。締切16日前のリスク管理

1. **奏でた湖面**: プレイ中のハメ/投下が湖面に波紋・光・色を刻み、曲終了時に「あなたが奏でた湖面」が一枚の風景として完成。曲別の個性=波紋の言語（T=碧のEDM波形リング+白鳥座の星、世=涙の波紋+色の灯り、シ=ストロボの鏡像反射）

3. **蝶の羽化**: プレイの多様性が蝶を育て、リザルトで羽ばたく。ひまわり・蝶・音符を成果物の装飾言語に
4. **湖畔のライブ**: 成果物=自分が照明/演出を務めたミクの湖上ライブの一場面（ミクの存在表現の直球）。浜松=楽器の街 → 鍵盤/楽器ピクトグラムが造形語彙
5. **湖の三楽章（連作構造）**: 3曲の成果物が同じ湖の異なる時間帯/楽章として並び、3枚揃うと「マジカルミライ2026の一日」が完成 — 3曲拡張の一貫性そのもの

**ユーザー反応（2026-06-13）**
- **「ハメ=波紋」変換: 採用**（とても良い）
- 種の組み合わせ: **1×4（奏でた湖面×湖畔のライブ）か 2×4（湖上の光譜×湖畔のライブ）** のどちらか。全体構成・評価基準を考慮した開発面/評価面の見通しで決めたい（→ファシリテーターに比較分析依頼）
- 成果物の物理形態は組み合わせ決定後に検討

**【ファシリテーター比較分析】1×4 vs 2×4**

| 観点 | 1×4 奏でた湖面×ライブ | 2×4 湖上の光譜×ライブ |
|---|---|---|
| 成果物の性質 | 風景画（波紋の干渉が積分された湖面+ミク） | 演奏記録（時間軸を持つ光の譜面+ミク） |
| **解法筒抜け要件との整合** | ◎ 時系列が干渉に積分され解法が読めない。結果の豊かさだけ残る | △ 譜面=時系列記録なので「いつ何をしたか」が読める方向の力。抽象化で緩和可能だが譜面性と秘匿性がトレードオフ |
| 目的関数との結合 | ◎ 多様性→波紋の干渉の豊かさ、偏り→単調な水面、として自然に絵に出る | ○ 密度・色で出るが直接的（=解法が見えやすい） |
| 画の強度（素材ハンデ下） | ◎ 風景画は「誰が見ても綺麗」を作りやすい。水面反射・波紋はWebGL定番で参考実装豊富 | ○ 抽象記譜は美しくするのにデザイン職人性が要る。「綺麗な点群」止まりのリスク |
| イノベーションの尖り | ○ 「演奏が風景を作る」は分かりやすいが前例感も中程度 | ◎ 「スコア（点数）とスコア（譜面）の二重意味」は概念として尖る |
| クリエイティビティ（楽曲同期の見え方） | ◎ ハメ→波紋が直感的・即時 | ○ 軌跡の蓄積は間接的 |
| 投票映え | ◎ プレイごとに違う風景=シェア映え | ○ 抽象美は人を選ぶ |
| 開発コスト | 波紋シェーダ調整（参考実装多数） | 譜面レイアウトの試行錯誤 |

**統合オプション（棄却可）**: 種2の魅力（軌跡の光）は**プレイ中の演出**として移植可能 — ハメの光が湖上を漂い、最終的に**湖面に溶けて積分される**（=成果物は1×4の風景）。「演奏の記録が景色になる」という物語で両者が繋がり、筒抜け問題も回避される。

### STEP 5.5 確定: 成果物 = 2×4（湖上の光譜 × 湖畔のライブ）（2026-06-13 ユーザー決定）

**物理形態の仕様（ユーザー原案）**
- **音符が水面と干渉**し（干渉の模様エフェクトを追加したい）、**水に溶けていくエフェクト**と共に**湖面を満たしていく**
- **満たし具合（fill level）が色のグラデーション**を発生させる
- グラデーションの**色彩は4段階のランキング（ランク帯）ごとに別の色彩**
- ランクの可読性: **色彩 + 湖面の水位**、または**より表現に富んだ方法**（→ファシリテーターに案出し招待）

**ファシリテーター注記**: 「音符が水に溶けて積分される」というユーザー設計により、2×4でありながら**時系列（解法）は最終成果物から読めない** — 筒抜け要件(制約3)は自動的に満たされる。光譜の魅力（音符・記譜性）はプレイ中の演出として生き、成果物では溶けて色になる。

**要確認**: 「4段階のランキング」= ランク帯が4刻み（例: C/B/A/S）という意味か（先のランキング階段4段目=外部API採用とは別の話と解釈）

### STEP 5.5 クローズ: 成果物の確定仕様（2026-06-13 ユーザー決定）

1. **「4段階のランキング」の意味確定**: 共有単位（数値スコア＋ランク）の**ランクと成果物を統合したもの**。ランクは4段階で、成果物（湖の静止画）がランク表示そのものを兼ねる — 共有される一枚にスコア・ランク・造形が一体化
2. **成果物は静止画**
3. **ランクに応じて生態系がテーマに合わせて変化**（ひまわり・蝶・白鳥等の生態系案を採用）
4. **開発方針: MVP→クオリティ漸進** — 生態系候補を全て表現できれば最高だが、素材問題・モデリング困難性があるため、MVPから段階的に質を上げる（縦切り先行と整合）

**成果物まとめ**: プレイ中、音符が水面と干渉し溶けて湖面を満たす（光譜の演出）→ 曲終了時、満たし具合の色グラデーション＋4段階ランク別の色彩世界＋ランク連動の生態系（MVPから漸進）を持つ**「あなたが奏でた湖」の静止画**が、スコア・ランクと一体の共有単位として出力される。時系列は溶けて積分されるため解法は読めない。

### STEP 7: UXループ詳細（2026-06-13 開始）

**確定事項から組み上がるループ骨格**
```
[ハメ] タップ(2拍基調+サビバースト) → 音符が湖面に落ち波紋干渉+EDM SE → 湖が満ちる
[投下] ハメで溜めたリソースを見せ場(6箇所)で投下 → 演出と満ち方が跳ねる
[終了] 満ち具合→色グラデーション+4段ランク+生態系 = 成果物静止画(共有単位)
[再戦] 「まだ奥がある」開示 → 投下配分・多様性の組み替え(ハック) → リプレイ
```

**未決スロットと選択肢（ファシリテーター提示・ユーザー判断待ち）**
- **A. 投下リソースの正体**:
  - A1 ゲージ型「響き」: ハメ成功で蓄積→見せ場で投下すると音符大型化・多重波紋。ポートフォリオ=どの見せ場に投下するか（投下可能回数 < 見せ場数 = 一回性）
  - A2 パレット型「音色」: 投下=ハメ音符の音色/エフェクト種の切替。多様性逓減と直結（同音色の連用は湖の色が偏り逓減）。ポートフォリオ=どの区間にどの音色を割るか
  - A3 合成（ゲージ×パレット）: 最も深いが複雑度最高
- **B. ハメ判定の床**: 「失敗が存在しない」設計案 — タップすれば必ず音符は落ちる（小さくても）。判定差はスコアと満ち効率にのみ反映、演出は破綻しない（層1-2保証、操作の強制なしと整合）
- **C. ウォームアップ区間の中身**: ビートプレビュー（メトロノーム波紋で自由練習）/ クラップ誘導（Clap to the Beatの予告として観客クラップ風）/ 1画面の操作提示 — 組合せ可、尺の目安4〜8秒
- **D. 一回性の置き場所**: 投下回数制限 / 音色の使用回数制限 / 両方
- **E. リプレイ動機の閉ループ**: リザルトで「満ちなかった水域」「出会えなかった生態系」「投下しなかった見せ場」の**存在だけ**をチラ見せ（解法は見せない）= 層2→層3境界の「まだ奥がある」

### STEP 7 ユーザー意思決定（2026-06-13）

**B（失敗が存在しない床）: 採用。C（ウォームアップ）: 採用**（中身の組み合わせは設計フェーズで詳細化）

**【コア機構のユーザー独自設計】Y軸音程ハメ（A案を置き換える別解）**
1. **サウンドエフェクトは画面のY軸に沿って音程の高低が発生**する（タップ位置の高さ＝鳴る音の高さ）
2. 各ハメ点には**JUSTのタイミングとJUSTの音程**が存在し、**両軸とも近いほどスコア増加**
3. **タイミング・音程のいずれか成功でゲージ蓄積**（両方成功でより蓄積）
4. **（タイミング, 音程）が「同じであるべきでない箇所」で同じ音ハメをするとスコア逓減**（多様性逓減の具体化）
5. **音ハメの最大合計回数を予め設定**（一回性の具体化）→ **限られたタップ回数をどの瞬間に配分するかがポートフォリオ**になる

**E の確定**: リザルトで**ランキングを表示**＋**「あとどれくらいスコアで生態系が変化するか」をバーで表示**（次の変化までの距離だけを見せる＝解法は見せない）

**ファシリテーター注記（この設計の含意）**
- 1回のタップ（位置Y＋タイミング）に「ハメ快感」と「予算配分」の2チャンネルが同居する極めて筋の良い統合。観る時間（タップ温存）も戦略になり、層1（見るだけ）と層3（ハック）が同じ行為の濃淡で繋がる

- 外部ランキング採用のため、スコアのクライアント改竄耐性が技術調査項目に追加

### STEP 7 続き: ユーザー意思決定（2026-06-13）

1. **X軸=エフェクト色**: タップ位置のX軸の変化によって、エフェクトの色がグラデーションで変化する → タップは **(タイミング, Y=音程, X=色)の3次元の表現行為**になった（プレイヤーは音程と色で湖を描く）

**【解析結果】（librosa=mcp-music-analysisと同エンジンをローカル実行 + TextAlive songmap）**
- **メロディ直接抽出（pyin）はフルミックスでは不成立**: 有声判定できた文字は66/1157（6%）のみ。EDMミックスでは楽器がボーカルf0をマスクする。測定できた59文字中**73%はコードトーン上**（コード格子がメロディの良い代理になる根拠）
- **コードデータは強力**: TextAlive音楽地図から210個・17種のコード、中央値0.69秒（約1.4拍）で変化する速い和声リズム。Fm/Eb/Cm/Db/DbM7/C が主要
- **繰り返しフレーズの音響類似度**: 同テキストフレーズ間のクロマ類似度 平均0.967（ランダム対比0.943）— 繰り返し箇所は音楽的にもほぼ同一（構造繰り返しの裏付け。ただし判別力は弱く、cの設計はsongmap構造データを正とする）
- 拍子=4/4確定（position max 4）。`docs/analysis/takeover-melody.json` に測定できた66音を保存（参考用・低信頼）

**【仕様提案 b】JUST音程 = コードトーン格子（chord-tone lattice）方式**
- Y軸を7スロット程度に分割し、**その瞬間のコード構成音（約2オクターブ分）にマッピング**。どの高さを叩いても必ず協和音が鳴る（=B「失敗が存在しない床」と完全整合。外れ音が物理的に存在しない）
- **JUSTスロット**はオフライン解析で事前計算して曲プロファイルJSONに格納: クロマ顕著度（その瞬間に最も鳴っている構成音≈メロディ近傍）で決定。信頼度が低い箇所はルート/5度の交互をフォールバック
- 根拠: 測定可能だったメロディの73%がコードトーン上 / コードデータは音楽地図で固定済み・3曲全てで自動生成可能（手置き譜面不要でスケールする）/ 規約上も安全（自作生成データ）
- 将来の精度向上オプション（技術調査フェーズ）: ボーカル分離（demucs等）→pyin再実行でJUSTスロットをメロディ実音に寄せる
**【仕様提案 c】多様性逓減の単位 = 繰り返し構造ペア + 二層ルール**
- songmapから**自動生成できる「繰り返し構造マップ」**を単位にする: ①同テキストフレーズ群（TAKEOVERは8種20回。Clap to the Beat 24s/189s対など）②サビ区間の再来（3回）
- **二層ルール**:
  - 「同じであるべき箇所」= 同一フレーズ内・同一コール窓内の連続ハメ → 同じ(タイミング,音程)comboはモチーフとして許容（微ボーナス）
  - 「同じであるべきでない箇所」= **構造の繰り返し2回目以降**（2回目のClap窓、サビ再来、対句ラップ）→ 1回目と同じcomboパターンは逓減、変化はボーナス
- 根拠: 繰り返し箇所は音響的にもほぼ同一（類似度0.967）=音楽が同じことをする場所でプレイヤーだけが変化する、という「ハック」の必然性が生まれる / 全てsongmapのテキスト等値+セグメントデータから自動算出可能（3曲スケール）

### STEP 7 クローズ: b確定・cのユーザー定義による上書き（2026-06-13）

- **b: コードトーン格子方式で確定**（Y軸スロット数は設計フェーズで最終化）
- **c: ユーザー定義で確定** — 逓減の基準は「JUSTパターンとの関係」:
  - **「同じであるべき箇所」= (タイミングの間隔, 音程)の同一連続が、音ハメとして成功するべき位置を取っている状態**（楽曲のリフ反復: Clap Clap Clap / Na Na Na 等）。ここでは同一comboの連続=正解であり**逓減しない**
  - **元楽曲を解析して「同一連続がJUSTである区間」を抽出し、逓減判定を調整する**（プロファイルに焼き込む）— 解析パイプラインの要件
