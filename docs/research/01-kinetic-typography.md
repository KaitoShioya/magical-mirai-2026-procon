# 調査詳細：キネティックタイポグラフィ

キネティックタイポグラフィとは、文字そのものの位置・大きさ・回転・透明度を時間に沿って変化させ、文字の動きで楽曲のリズムと感情を表現する技法である。本作では疾走感の主役に据える。描画ライブラリはthree.jsに統一済みのため、本文書はthree.js上での実現方式を確定形で記す。

## 1. 採用する文字描画の方式

### 結論
3次元空間の演出文字はtroika-three-textで描く。読ませるための歌詞はブラウザの文書要素（HTMLのDOM）にGSAP（アニメーションを制御するライブラリ）を組み合わせて最前面に重ねる。成果物の画像に焼く文字はtroika-three-textで描き直す。

### 採用理由
日本語は漢字を含めて表示しうる文字数が数千に達する。文字の輪郭をあらかじめ画像の地図（アトラス）に焼く方式は、漢字の地図が巨大になり、課題曲の歌詞が変わるたびに作り直す運用が必要になる。troika-three-textはフォントファイルを実行時に解析し、実際に使われた文字だけを符号付き距離場（文字の輪郭からの距離を画素値として持ち、拡大しても輪郭が鮮明になる表現。英語の頭文字でSDF）として動的に生成する。文字の解析と距離場の生成と配置の計算をWeb Worker（画面描画とは別の処理系統）で行うため、描画が滑らかさを失わない。これにより、地図を事前に焼く運用の負担が消える。

文字の押し出しによる立体化（TextGeometry）は、漢字の曲線が多く頂点数が膨らみ、高速で多数の文字を出す本作では毎秒60フレームを保てないため採用しない。

## 2. 文字単位の制御方式

troika-three-textは1つの文字列を1つの結合した立体として描くが、内部では各文字を四角形の単位として持ち、頂点シェーダ（頂点の位置を計算するGPUのプログラム）に各文字の境界の矩形の情報を渡している。文字単位の動きは次の2方式で実現する。

- **インスタンス分割**：1文字ごとに文字描画の単位を作り、位置・回転・大きさ・透明度をGSAPで個別に動かす。自由度が最も高い。文字数が多いと処理系統の負荷が上がるため、同時に存在する数を抑える。
- **シェーダ注入**：派生マテリアルの仕組み（`createDerivedMaterial`）で頂点シェーダに計算を差し込み、各文字の矩形情報を使って、文字全体をまとめて1回の描画命令で変形する。渦・波打ち・残像のような全文一括の派手な動きに使う。処理系統の負荷を避けられる。

## 3. 演出文法6種の実装

参考にした映像（かいりきベア「メンタルチェーンソー」）から抽出した6つの技法を、three.js上の実装に対応づける。

| 技法 | 内容 | 実装方式 |
|---|---|---|
| 1文字1拍の切り替え | 1文字を拍に正確に合わせて瞬間表示する | インスタンス分割。各文字の表示と大きさと透明度をGSAPで拍の時刻に瞬間設定する。同時存在数を抑える |
| 全文一括と字間の拡大保持 | 文を一度に出し、文字の間隔を広げて数拍保持する | 1つの文字列の文字間隔の値をGSAPで補間する。1回の描画命令で済む |
| 同一語句の円状回転と重ね増殖 | 同じ語句を円周に並べて回す、または一点に重ねて増やす | 同じ文字列の描画単位を複数作り、親の物体にぶら下げ、極座標で配置して親を回す |
| 長い音の縦伸ばしと渦 | 長く伸びる音で文字を縦に伸ばす、または渦を巻かせる | 縦伸ばしは縦方向の拡大の補間。渦はシェーダ注入で各文字の中心から角度に応じたねじりを頂点に加える |
| 残像 | 動く文字に尾を引かせる | 過去の数フレームの位置に半透明の文字を重ねる方式、または前のフレームの描画結果を減衰させて重ねる方式。スマートフォンではこの2方式を使う |
| 減衰と暗転 | 楽曲の終わりや切れ目で文字を消す | 文字の塗りの透明度を0へ補間する |

参考映像はもう1本ある（DECO*27「テレパシ」、`docs/refs/reference-analysis.md` 第1B節）。明るいポップ系の文法として、2色の反転による場面転換、図形からの文字構築、疑似UIと記号の装飾（破線枠・音声波形・円・×記号）、網点と斜線のテクスチャ、極太ゴシックのはみ出しスマッシュを補う。これらの装飾図形はすべてコードで描ける。本作の世界観は深夜で暗いため、参考映像の明るい配色はそのまま使わず、構造（粒度の切替・スマッシュ・はみ出し・句読点・装飾図形）だけを取り、色と質感は発光する文字（発光マテリアルとブルーム）と、オレンジとネオンブルーの差し色へ置き換える。

## 4. 3次元のカメラ移動による文字演出

three.jsの透視投影カメラ（遠近を表現するカメラ）で、3次元空間に置いた文字の間をカメラが移動・回転する。文字が手前へ飛ぶ、奥へ抜ける、遠近が強調される、という疾走感を作る。被写界深度（焦点の外側をぼかす表現）と動きのぼかしは効果が強い反面、処理の負荷が高いため、解像度を落とした描画領域で適用し、見せ場の区間だけ有効にする。

常在するミクは湖の中心の固定点に在り、カメラはこの中心を見せ場の区間で框取りする。テキストタイポグラフィとミクと空間の3者が同時に最大の主張をしないよう、主役を時間で切り替える。文字を主役にする瞬間はミクを暗めにし遠景へ退かせ、空間と演出を主役にする瞬間にミクの照明と框取りを強める。この分担は `docs/research/02-non-text-expression.md` の主張の分担に従う。

## 5. 読ませる歌詞と演出文字の役割分担

読ませることを最優先する主役の歌詞は、ブラウザの文書要素にGSAPを組み合わせて最前面に重ねる。理由は、ブラウザの文字描画は常に画素単位で鮮明であり、日本語の太いゴシック体の字詰めが最も読みやすいためである。3次元空間で動く演出の文字はtroika-three-textで描き、湖面と音符と同じ描画空間で前後関係を正しく合成する。

成果物の画像はブラウザの文書要素の文字を含められない。理由は、WebGLの描画結果の取り出しに文書要素は含まれないためである。よって成果物に載せる文字はtroika-three-textで描き直す。成果物は構図が確定した静止画であり処理の制約が緩いため、troika-three-textで高品質に組める。

## 6. フォント

日本語の太いゴシック体で、商用利用と改変とWebへの埋め込みが許可されたものを使う。条件を満たすのはNoto Sans JP、Zen Kaku Gothic New、M PLUS 1の3書体で、いずれもSIL Open Font License（フォントの自由な利用と改変と再配布を認めるライセンス）で配布される。フォントは自分のサーバに置き、課題曲の歌詞に現れる文字だけを抜き出して読み込み量を減らす。

## 7. 175BPMでの性能対策

性能の律速はtroika-three-textの描画単位ごとの計算であり、数千の描画単位で処理系統の時間の3割から5割を消費する報告がある。これを避けるため次の3点を行う。

- **事前生成**：楽曲の読み込み時に、課題曲に現れる全ての文字を一度描画して符号付き距離場の地図を温めておく。これにより、文字が初めて出るときの生成の遅れが本編で起きない。
- **再利用**：同時に存在する文字描画単位の数に上限を設け、出現と退場で使い回し、生成と破棄を避ける。
- **一括描画**：多数の文字を1回の描画命令にまとめる機能（BatchedText、バージョン0.50以降）を使い、派手な全文一括の動きはシェーダ注入で1回の描画命令にする。

TAKEOVERは総文字数1157、文字密度の最大が毎秒8.3文字、短い音の文字の比率が55パーセントである。この密度でも上記3点で毎秒60フレームを目指す。

## 8. 楽曲との同期

楽曲の再生位置の正典はTextAliveの`player.timer.position`（ミリ秒単位の再生位置）である。GSAPのタイムライン（一連のアニメーションの時間軸）を自走させず、各フレームで再生位置を読み、タイムラインをその位置へ移動させる。これにより、利用者がシークしても巻き戻しても破綻せず、音と映像がずれない。拍の確定値はTextAliveの音楽地図（拍の識別番号で固定したもの）を正典とする。

## 9. 感情と声量と発光への対応

採用理由を先に述べる。テキストタイポグラフィは本作の最重点の1つで、ビートとテンポと歌詞の感情を動的に表す必要がある。TextAliveは感情の値（valenceArousal）と声量の値（vocalAmplitude）を提供するため、これらを文字の見た目へ写像できる。声量を文字の太さと大きさに、感情を色と動きの激しさに、拍を文字の入りとカットに対応づける。

舞台は深夜の湖のため、3次元空間の演出文字は発光マテリアルで描きブルームでにじませる。読ませる主役の歌詞は可読性を保つため発光を抑え、縁取りと影で背景から分離する。テキストは楽曲の進行に従い、各表示の役目が終わると透明度を0へ補間して消える。

### 表示粒度の切替（疾走感の核）
採用理由を先に述べる。2本の参考映像に共通する疾走感の正体は、歌詞の発声属性に応じて表示の粒度を数拍ごとに切り替えることである。粒度は文字・単語・フレーズ・画面全体の4段で、TextAlive の各単位の継続時間と声量と感情から選ぶ。

| 歌詞の発声属性 | 表示粒度と表現 | 判断に使う値 |
|---|---|---|
| 強い口調・短い音 | 1文字を1拍で画面いっぱいにスマッシュし、はみ出させる | 文字の継続時間が短い |
| 流れる連続フレーズ | フレーズを一括表示し字間を広げて数拍保持する | フレーズの継続時間が長い |
| 同一フレーズの連発 | 円状に並べて回す、または一点に重ねて増やす | フレーズ文字列の重複（事前計算） |
| ロングトーン・シャウト | 文字を縦に伸ばす、渦を巻かせる | 文字の継続時間が長く声量が大きい |
| 曲の切れ目 | 暗転、または細い手書き風の文字で静かに転換する | ビートと区間の境界 |

短い文字と長い文字の境界、密度の山と谷の境界は、各曲の音楽地図の実測値を初期値とし、実装後のプレイ検証で調整する。TAKEOVERは文字の55パーセントが短い音で密度の最大が毎秒8.3文字のため、1文字1拍のスマッシュは2拍に1回へ間引き、最長30.3拍のラップ区間は流し込みにする。

参考映像の音響解析（`docs/refs/reference-analysis.md` 第1B.4節）から、表示粒度の切替はビート格子に、細部の動き（装飾図形や文字の段階的構築）は音の立ち上がりに乗ると確認できた。課題曲ではビート格子は TextAlive 音楽地図が正典であり、細部の動きは声量（vocalAmplitude）の山に乗せる。

文字の装飾図形（破線枠・記号・網点・図形からの文字構築）は、すべてコードで描き、発光する文字と差し色の世界観に合わせて再配色する。
