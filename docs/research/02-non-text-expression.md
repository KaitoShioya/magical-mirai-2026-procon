# 調査詳細：テキスト以外の表現

本作は手描きイラストの自作を前提にしない。少ない素材を、コードによる動的な描画と映像編集の技法で最大限に見せる。例外として、ミクは規約に適合する自作モデルを読み込み、舞台の土台（陸地と水際の地形）も静的な3Dモデルを読み込む。地形は動的に変える必要がなく、コードで生成するのは見通しと最適性に反するためである。それ以外（水面の反射と揺らぎ、雨、発光の灯し）はコードで描く。本文書はその技法と、ミクおよび灯しの描画方式を確定形で記す。

## 1. コードで実現する映像編集の技法

次の技法はすべてコードで描ける。費用対効果が高い順に上位5つを採用の中心に置く。適合度はTAKEOVER（毎分175拍の疾走する電子音楽）と湖のテーマとスマートフォンと、テキストを主役に保つことを基準に判断した。

| 技法 | 内容 | 採用度 |
|---|---|---|
| 拍に同期した拡大と減衰する揺れ | 拍ごとに画面を一瞬拡大し、揺れを減衰させる。疾走感の核を最小の負荷で生む | 最優先 |
| 湖面の平面反射と雨 | 暗い湖面に光点と空を映し込み、環境としての雨の筋と揺らぎを描く。深夜の世界観と発光の灯しに直結する。水面の領域は舞台の土台モデルが定義し、反射はその水面領域に適用する | 最優先 |
| 明部の発光（ブルーム）と周縁減光（ビネット） | 明るい部分をにじませて発光させ、画面の周縁を暗くして視線を中央へ導く。灯しの輝きの主役 | 最優先 |
| 一瞬の色収差 | 赤・緑・青の画素を一瞬ずらして衝撃を出す。楽曲の強い拍で使う | 高 |
| 発光する灯しの配置 | 楽曲終了後に、ひまわりと蝶を発光する造形としてコードで描き湖面へ配置する | 高 |

採用しない、または限定して使う技法は次のとおりである。グリッチ（画面を破壊するノイズ）と全画面の点滅は、文字の可読性を損ない光の刺激が強いため、文字の背面と一瞬の使用に限り、消す設定を用意する。常時の発光と被写界深度は演奏中の拍の感覚を弱めるため、演奏中は雰囲気の土台としてのみ使い、発光を主役にするのは楽曲終了後の灯しの情景とする。タップの位置から広げる操作の波紋は廃止し、雨は環境の演出とする。

## 2. 拍への同期の作り方

拍の検出は音声の周波数解析では行わない。理由は、本作の楽曲はTextAlive経由で再生され手元に音声ファイルがないこと、そしてTextAliveの音楽地図に拍の時刻があらかじめ含まれていることである。よって、楽曲の読み込み時に拍の時刻の配列を読み、各拍に視覚の出来事を割り当てる。毎フレームで再生位置を見て、直前の拍を跨いだフレームでその出来事を1回だけ発火させる。各出来事は短い立ち上がりと減衰で消える。毎分175拍では1拍が343ミリ秒のため、1回の出来事は80ミリ秒から150ミリ秒に収める。

## 3. テキストと非テキストの主張の分担

文字を主役にする瞬間と、演出を主役にする瞬間を、画面の前後関係と注意の誘導で分ける。原則は「同時に最大の主張をさせない」である。具体的には、文字を主役にする瞬間は背景の演出の動きを止めて背景を暗くし、演出を主役にする瞬間は文字を小さく退かせる。歌詞のない間奏と無音の瞬間こそ演出を強める。文字には常に縁取りと影を入れ、どの背景でも最低限の可読性を保つ。常在するミクも空間表現の柱の一部として、この分担に従う。文字を主役にする瞬間は、ミクを暗めにし遠景へ置き、または画面の框の外へ外して退かせる。演出と空間を主役にする瞬間に、ミクの照明と框取りを強める。

## 4. ミクの描画

### 結論
ミクは VRoid Studio で人間が二次創作モデルを自作し、VRM（glTF 形式）で書き出して `@pixiv/three-vrm` で読み込み、コードで照明と反射と動きを動的に描画する。適切なスケールで湖の中心に配置し、舞台構成の一要素としてプレイ本編の開始時から常在する。MVPではポーズを固定し、モーションは後から付加できる設計とする。

### 採用理由
規約の境界は素材をAIが生成したかどうかである。VRoid Studio は人間がスライダーとブラシで造形するため人間の制作物にあたり、AIが生成したモデルの禁止に抵触しない。認識可能なミクを最重点のグラフィック品質で出すには、純粋なコード描画より自作モデルの読み込みが確実である。読み込んだモデルの照明・反射・動きはコードで動的に描くため、動的な表現の生成にあたる。規約とライセンスの詳細は `docs/research/05-asset-procurement.md` に記す。

### 仕様
深夜の湖の照明と湖面の反射に合わせてモデルを描画する。ピアプロ・キャラクター・ライセンスの指定文言と、クリプトンのキャラクター利用のガイドラインに従う旨をアプリ内に常に表示する。公式のイラストをなぞることは複製にあたるため行わない。

### 本編中の常在と描画
ミクは舞台構成の一要素として、プレイ本編の開始時から湖の中心に常在する。深夜・雨の暗い舞台では、輪郭を縁取る光（リムライト）と発光の差し色でモデルを背景から分離する。ミクは平面反射・ブルーム・影の対象に含める。平面反射は世界を鏡像の位置のカメラでもう一度描く方式のため、スキンメッシュであるミクを反射に含めると反射の描画負荷が増える。負荷が高い場合の縮退の順序と計測の方法は `docs/research/03-rendering-ui.md` に定める。

### モーションの後付け設計
MVPではポーズを固定する。モーションは後から付加できる設計とし、ボーンを操作する層を抽象化する。`@pixiv/three-vrm` の `VRMHumanoid` でボーンの回転をコードで与える方法（手続き的なモーション）と、`@pixiv/three-vrm-animation` でVRM Animationを読み込み `createVRMAnimationClip` から `THREE.AnimationMixer` で再生する方法（人間が手付けした、または配布されたモーションの再生）の双方を、同じ抽象の差し替えで扱えるようにする。モーションの素材源の規約適合は `docs/research/05-asset-procurement.md` に整理する（採否は保留、MVPはポーズ固定）。

## 5. 灯しのコードによる描画

すべてコードによる数式の描画で、AIの素材を使わない。ひまわりと蝶は、楽曲終了後に湖面へ配置する発光する灯しである。反応強度の写像は、タイミング精度を大きさ、音程精度を輝度に対応させる（両者とも）。色は固定のためスコアに寄与しない。

- **ひまわり**：各ノーツ点の真下、湖面に浮かぶオレンジ色に光る造形。形は、種と花弁を黄金角（約137.5度）に基づくフェルマー螺旋で配置して作る。採用理由は、この角度が外周ほど密度を均一にし、実際のひまわりの種の並びを再現するためである。種の位置は、中心からの距離をn番目の種について「定数×nの平方根」とし、角度を「n×137.5度」とする。
- **蝶**：空間上のノーツ点の位置に置くネオンブルーに光る造形。左右対称の翅をパラメトリックな曲線で描く。演奏中はハメた瞬間に舞って消えるノーツ効果として使い、楽曲終了後は反応強度に応じた灯しとして配置する。
- **白鳥**：初期の実装範囲から外し、後の拡張候補とする。

### 灯しの配置（目標形の保証）
採用理由を先に述べる。配置は、反応強度が理論最大のときの目標形が、どの楽曲・どのカメラワークでも自然で美しい構図になることを保証する必要がある。楽曲終了後の灯しの配置は、カメラワークが決めた各ノーツ点の位置を素案とし、ボロノイ緩和を2から4回かけて均す。各点を自分の縄張りの重心へ寄せる操作を少数回繰り返し、近すぎる点を離し空きすぎを詰める。少数回で止める理由は、完全収束させると整然均一になり、自然なゆらぎと楽曲の個性が消えるためである。各点の移動量に上限を設け、全体の形（楽曲の個性）を保つ。固定色の発光造形のため、配置がランダムでも、反応が0・部分的・最大のいずれでも自然に美しい湖面の灯しになる。具体回数と移動量の上限は実装後のプレイ検証で決める。ボロノイ緩和はミクの位置を決めず、灯し分布のゆらぎを均す役割に限定する。湖の中心は舞台の固定点であり、カメラ軌跡を見せ場区間でこの中心へ偏らせることで、灯し分布の密集点が中心と一致する。

最初に実装するのはひまわりである。
