# 調査詳細：湖面のレンダリングと色彩と操作音

本文書は、プログラムが生成して利用者が受け取る視聴覚のうち、湖面の反射、色彩の変化、毎秒60フレームの予算、音程付きの操作音について、確定形で記す。描画ライブラリはthree.jsに統一済みである。

## 1. 湖面の反射と雨と発光

### 結論
舞台の土台（四方を囲む陸地と水際の地形）は静的な3DモデルをglTFローダーで読み込み配置する。地形は動的に変える必要がなく、コードで生成するのは見通しと最適性に反するためである。湖面の反射は平面反射方式を基本とし、土台モデルの水面領域に適用する。水面領域は、土台モデル内の約束した名前のメッシュ（名前を water とする）で識別する。採用理由は、名前で識別すればモデルを差し替えてもコードを変えずに水面を特定でき、人間が用意するモデルとコードの反射適用を疎結合にできるためである。発光する光点にはブルーム後処理でにじむ光を作る。雨は環境の演出として描き、操作の判定には関わらない。画面空間反射の高品質な方式は負荷が高いため、中心の見せ場のみ限定適用を検討する。

### 採用理由
舞台は深夜・雨の湖で、暗い湖面に発光する灯しと空が映り込む絵が世界観の核である。平面反射方式は、水面を鏡とみなし、鏡像の位置のカメラで世界をもう一度描いて映り込みを作る方式で、平らな水面に適し負荷が抑えられる。発光する点は、発光マテリアルとブルーム後処理でにじませると、湖面の灯しの輝きになる。夜景は可視ジオメトリが少なくブルームが主役のため、スマートフォンでの毎秒60フレームと両立しやすい。画面空間反射は画面に描いた結果の上で光線を辿る方式で品質は高いが負荷が大きいため、中心の見せ場に限る。旧仕様のタップによる操作の波紋と水位上昇の演出は廃止する。

### 用語
- 平面反射：水面を鏡とみなし、鏡像の位置のカメラで世界を描いて映り込みを作る方式。
- ブルーム：明るい部分をにじませて発光に見せる後処理。
- 画面空間反射：画面に描いた結果の上で光線を辿り、映り込みを作る方式。

### 検証（試作の結果）
試作は `prototype.html` と `src/prototype/main.js` に置いた。平面反射（Reflector）、発光のブルーム（UnrealBloomPass）、発光点（InstancedMesh）、雨、troika の文字、移動する透視投影カメラを単一の描画領域で組み、エラーなく描画できることを確認した。暗い湖面に映り込むオレンジとネオンブルーの発光点という狙いの見えも確認できた（湖面の下半分に光点と文字の鏡像が出る）。

毎秒60フレームは、GPUのある Chrome ブラウザでの確認で、起動画面が平均しておおむね保たれることを確認した。よって本構成（平面反射・半解像度ブルーム・発光点・雨・文字・移動カメラ）は毎秒60フレームの予算に収まる。

なお、本開発環境の自動計測ではこれを再現できなかった。理由を先に述べる。本環境にはGPUが無く、ヘッドレスの Chromium がソフトウェア描画（SwiftShader）にフォールバックするため、計測値（約2〜3フレーム毎秒）はソフトウェア描画の値であり実機の性能を表さない。残るのは、対象とするスマートフォンの実機での設定範囲の調整である。試作には URL クエリで反射解像度・ブルーム解像度・画素密度上限・インスタンス数・雨粒数を切り替えるノブを用意したため、実機での調整に使える。`npm run dev -- --host` で同一ネットワークのスマートフォンから開ける。GPUのある環境では `node scripts/prototype-fps.mjs` で自動計測できる。

## 2. 色彩と専用ゲージの色変化

### 結論
場面の色は固定する（深夜の空と暗い湖面、オレンジ色のひまわりの灯し、ネオンブルーの蝶の灯し）。連続的な色の変化が要るのは専用ゲージの色で、その補間はOKLCH表色系で行う。

### 採用理由
従来のHSL表色系は、色相を変えると人間が感じる明るさと鮮やかさが不均一に変動するため、2色の中間の色がくすんだり明るすぎたりする。OKLCH表色系は明度と彩度と色相を人間の知覚に沿って表すため、2色の中間が滑らかで均一になる。ランクは色彩の変化でなく専用ゲージで表すため、ゲージの4段階の色の連続的な変化に知覚的に均一な補間が必要である。旧仕様の湖の満ち方のグラデーションと、寒色から暖色へのランク色彩アークは廃止する。

### 仕様
専用ゲージの色はOKLCH表色系で定義し、スコアの蓄積に応じて4段階で連続的に変える。ゲージは判定レーンの上に表示し、投下ゲージとは別物とする。スコアとランクは撮影時にゲージの表示へ統合する。

## 3. スマートフォンで毎秒60フレームを保つ予算

### 採用理由
描画の負荷は、画面の画素数と、1フレームの描画命令の回数で決まる。スマートフォンは画面の画素密度が高く、何も対策しないと描画する画素が多すぎて毎秒60フレームを割る。描画命令の回数は、おおむね100回までで多くの端末が毎秒60フレームを保ち、500回を超えると高性能の端末でも保てなくなる、という実測の目安がある。

### 仕様
次の3点を行う。第1に、画面の画素密度の倍率を2までに制限する。第2に、発光と歪みのような重い後処理は、画面より低い解像度の描画領域で行う。第3に、音符と光点（湖面の灯し）は同じ形を1回の描画命令でまとめて描くInstancedMesh（同じ形を多数並べる仕組み）で描き、描画命令の回数を100回未満に保つ。実測で負荷が高い場合は画素密度の倍率と後処理の解像度を自動で下げる。

## 4. 音程付きの操作音

### 結論
操作音はWeb Audio（ブラウザの音声合成の仕組み）のオシレーター（基本波形を生成する音源）で合成する。サンプル音源の事前用意はしない。

### 採用理由
タップのたびにその瞬間の和音の構成音を鳴らすため、音の高さを自由に変えられる必要がある。オシレーターの合成は、音源ファイルが不要で容量がかからず、発音までの遅れが最小で、電子音楽の音色に合う。和音の構成音を画面のY軸の位置に割り当てるコードトーン格子と直接つながる。

### 仕様
タップのたびに、音源と音量調整の節点を新しく作り、発音し、減衰の後に停止し、停止の後に接続を切って記憶を解放する。音量を立ち上げる際は、急な変化による雑音を避けるため、3ミリ秒から5ミリ秒かけて音量を上げる。和音が切り替わる瞬間は、前の音を減衰させてから次の音を立ち上げ、切れ目の雑音を避ける。音色は、密な楽曲の上で他の音を覆い隠さないよう、立ち上がりが短く減衰の速い撥弦・鐘・木琴系を使い、300ヘルツより低い帯域を削り、1キロヘルツから4キロヘルツの帯域に置く。同時に鳴らす音の数に上限を設け（16から24）、上限に達したら最も古い音を短く消してから止める。スマートフォンでは、利用者の最初のタップで音声の仕組みを起動する。発音は判定や得点の計算と切り離し、タップの瞬間に即座に鳴らす。これにより、操作から発音までの遅れを利用者が自分の演奏として受け取り、不快なずれにならない。投下を発動したときは、発音中の音色に明るい倍音の層を1つ重ねて手応えを上げる。倍音を足す変化は元の音程を保ったまま音色だけ豊かにできるため、協和を崩さず強化された感覚を作れる。

### 後続の方針（ノーツ音の高品質化、Issue #169）
最小実装（Issue #52）はオシレーターの三角波による単純な音色である。最終的な作品では、ノーツ音を楽曲の雰囲気に合った効果音として、クオリティの高い楽器音（ドラム・ベース等）や打ち込み音楽制作（DTM）のような心地よい音へ差し替える。差し替えはすべてプログラム（Web Audio）による合成で行い、AI生成の音源や権利のあるサンプル音源（録音物）は組み込まない（規約は CLAUDE.md「表示する絵・音楽・文章にAI生成物を使わない」「素材は自作または適正ライセンス」に従う）。コードトーン格子・同時発音管理・起動・有効無効の切替は Issue #52 の仕組みを流用し、加算合成・周波数変調合成・減算合成・打楽器合成などで楽器らしい音色を作る。これは Issue #169 が担う。

## 5. 描画の層の合成

three.jsの1つの描画領域の中で、遠近を表現するカメラの3次元の世界（湖面と演出文字と灯し）を描き、次に深度の情報だけを消してから、動かない正射影のカメラ（遠近を表現しないカメラ）で2次元の層（判定レーンと入力グリッド）を最前面に重ねる。画面四隅の操作情報は、文字の鮮明さと実装の容易さのため、ブラウザの文書要素で重ねる。詳細は `docs/research/06-tech-stack-and-architecture.md` に記す。

## 6. ミク常在時の性能と縮退

### 結論
ミクは本編開始から湖の中心に常在し、平面反射・ブルーム・影の対象に含める。VRMモデルは肌や髪の頂点を多く持つスキンメッシュであり、平面反射に含めると反射のパスでもう一度描くため負荷が増える。スマートフォンでの毎秒60フレームを保つため、要因を分けて律速を特定する計測と、負荷が高い場合の縮退の順序を定める。

### 計測の方法（採用理由を先に述べる）
クラウドの自動実行環境にはGPUが無く、ヘッドレスのブラウザは既定でGPUを使わずソフトウェア描画にフォールバックするため、計測値は実機の性能を表さない。よって正式な合格判定は、GPUのある実機スマートフォン、または通常起動のブラウザ（ヘッドレスでなく仮想ディスプレイ上でGPUを使う構成、もしくは描画系統をANGLEに固定する起動引数を与えた構成）で行う。対象端末クラスは既存の `scripts/prototype-fps.mjs` のモバイルプロファイル（表示領域390×844、デバイス画素倍率3、処理能力6倍スロットル）を基準とし、正式判定の実機は1台以上、機種名・基本ソフト名・ブラウザ名とともに実装フェーズで確定する。測定は起動後の定常区間を10秒以上とる。合格条件は、平均だけでは瞬間的なカクつきを見逃すため、平均と下位5パーセンタイルの両方で毎秒60フレームの下限を満たすこととする。

### 計測ケース（要因を分けて律速を特定するため）
VRM常在あり／なし、反射パスにVRMを含む／含まない、ブルーム対象にVRMを含む／含まない、土台モデルあり／なし、の組合せで計測する。これにより、律速が頂点負荷・反射の再描画・後処理・画素数のどれかを切り分ける。土台モデルの陸地は静的ジオメトリで頂点数が固定であり、毎フレームの骨格変形を伴うスキンメッシュより軽い。

### 縮退の順序（採用理由を先に述べる。コスト削減が大きく見た目の損失が小さい順に落とすため）
第1に反射パスからVRMを除外する（反射は世界を再描画するためコストが大きく、湖面のミクの映り込みは情報量が小さい）。第2に影を簡易な接地影へ置換する（影の地図を作る方式は高コスト）。第3にブルーム対象からVRMを除外する。第4に頂点数とボーン数を下げた簡易版へ置換する。第5に画素密度の倍率を下げる。モーションはMVPで固定ポーズのため縮退の対象にしない。ただし計測で律速が判明した場合は順序を入れ替えられる。律速種別と優先する縮退の対応は次のとおり。頂点負荷が律速なら簡易版への置換を優先、反射の再描画が律速なら反射パスからのVRM除外を優先、後処理が律速ならブルーム対象からのVRM除外と後処理解像度の低下を優先、画素数が律速なら画素密度の倍率低下を優先する。陸地（土台モデル）を反射パスへ含めて負荷が高い場合は、陸地を反射パスから除外する。採用理由を先に述べると、陸地の水面への映り込みは情報量が小さく、削減の効果に対して見た目の損失が小さいためである。
