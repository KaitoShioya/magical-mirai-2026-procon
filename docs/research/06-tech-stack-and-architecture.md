# 調査詳細：技術スタックとアーキテクチャ

本文書は、アプリケーション全体の技術構成を確定形で記す。描画ライブラリの選定の理由は `docs/decisions/app-overall-decisions.md` に記したため、ここでは構成と実装の方針を述べる。

## 1. 技術スタックの一覧

| 領域 | 採用 | 採用理由 |
|---|---|---|
| プログラミング言語 | TypeScript | 型による安全性が高く、規約が求める読みやすい構成に合う |
| 画面の枠組み | フレームワークを使わない | 描画の繰り返し処理が主役であり、画面の差分更新を行うフレームワークは毎フレームの描画と二重管理になり害になる |
| 描画 | three.js | 3次元のカメラ移動と2次元の描画を1つの描画領域で扱える。複数の描画領域を重ねるとスマートフォンで上限に達して壊れるため、1つに統一する必要がある |
| 3次元の文字 | troika-three-text | 日本語の多数の文字を事前の画像地図なしで動的に描ける |
| ミクのモデル読み込み | @pixiv/three-vrm | VRoidで自作したVRMモデルを、GLTFLoaderに登録する公式の差し込みで読み込み、コードで動かせる |
| 舞台の土台モデルの読み込み | three.js の glTF ローダー | 陸地と水際を定義する静的な3DモデルをglTF形式で読み込んで配置する。地形は動的に変える必要がなく、ミクのVRMと同じ読み込み系統で扱える |
| 読ませる歌詞 | ブラウザの文書要素とGSAP | 文字が画素単位で鮮明であり、日本語の字詰めが読みやすい |
| 操作音 | Web Audio | 音の高さを自由に変えられ、音源ファイルが不要で遅れが小さい |
| 楽曲と歌詞 | TextAlive App API | コンテストの必須要件であり、楽曲と歌詞と音楽地図を提供する |
| ビルド | Vite | 既存の構成で、開発の即時反映と本番のビルドを行う |
| 配信 | Cloudflare Pages（Cloudflare Accessで限定公開）とGitHub Actions | GitHub Pagesは有料プランでもサイトが一般公開され規約の募集期間中の一般公開禁止に反するため採らない。Cloudflare Pagesは無料でアクセス制限でき、デプロイはGitHub Actionsで行う |

時刻の基準は、TextAliveの`player.timer.position`（ミリ秒単位の再生位置）を毎フレーム読む。three.jsの時計と描画の繰り返しの時刻は演出にのみ使い、判定の基準には使わない。

## 2. 入力アーキテクチャ（3空間分離）

### 結論
入力の判定面（動かない2次元）、演出のカメラ空間（動く3次元）、画面四隅の操作情報（動かない）の3つを分け、座標の変換を入力から演出への一方向だけに限る。

### 採用理由
演出のカメラが3次元空間を移動しても、操作の判定が破綻してはならない。3次元の物体との交差判定（レイキャスト）で入力を取ると、「外す」概念が生じて失敗のない床に反し、カメラの移動で交差面が動いて入力が壊れる。視点が動くリズムゲーム（Cytus、Arcaea、Phigros）は、判定を視覚のカメラから切り離し、画面座標で判定している。

### 仕様
タップの判定は、画面座標を0から1の範囲に正規化し、X軸の値を色に、Y軸の値を音程に、純粋な関数で写像する。カメラの行列を参照しない。複数の指の同時操作はPointer Events（マウスとペンと指を同じ仕組みで扱うブラウザの入力イベント）で受け、各接触に割り当てられる識別番号を鍵にした対応表で独立に管理する。スクロールと拡大を無効化するため、入力を受ける要素に`touch-action: none`を指定する。視覚のフィードバック（光点と音符）は、正規化した座標を動かない正射影のカメラ（遠近を表現しないカメラ）の表示範囲に写像して描く。

## 3. 描画の層の合成

three.jsの1つの描画領域の中で、次の順に描く。第1に、自動消去を無効にし、色と深度を消す。第2に、遠近を表現するカメラで3次元の演出の世界（湖面と灯しと演出文字）を描く。第3に、深度の情報だけを消す。第4に、動かない正射影のカメラで2次元の層（音符と光点と入力グリッド）を最前面に描く。これにより、3次元の前後関係に関わらず2次元の層が確実に手前に重なる。画面を区画に分ける方式は不要で、全画面に重ねる方式を採る。画面四隅の操作情報（得点、コンボ、ゲージ、ランクの百分位）はブラウザの文書要素で重ね、安全領域（切り欠きを避ける余白）に配置する。

## 4. 成果物の画像の書き出し

### 結論
描画結果を取り出す領域（RenderTarget）に成果物の構図を描き、画素を読み出して画像にする。

### 採用理由
描画結果を常に保持する設定（`preserveDrawingBuffer`）は、一部の端末で常時の描画の性能を下げるため常用しない。描画結果を取り出す領域に専用に描けば、常時の負荷を増やさず、画面より高い解像度で成果物を描ける。すべての要素が1つの描画領域にあるため、合成の手間がない。

### 仕様
成果物の画像は、ブラウザの文書要素の文字を含められないため、成果物に載せる文字はtroika-three-textで描き直す。画像の取り出しは、利用者が保存の操作をした起点で行う。スマートフォンの画像の最大の面積の制限を避けるため、画素密度の倍率を掛けず固定の画素数で作る。画像はファイルとして共有の仕組みに渡し、対応しない場合は保存とテキストの共有に切り替える。

## 5. バンドルと配信

three.jsは、最小化しても容量が大きく不要部分を取り除きにくい構造のため、必要な部品だけを名前付きで取り込み、追加の部品は使うものだけを個別に取り込む。reactを使う構成（react-three-fiber）は採らない。理由は、reactへの依存を持ち込まず、容量と読みやすさを保つためである。配信はCloudflare Pagesで行い、GitHub Actionsで自動化する。`<プロジェクト名>.pages.dev` のルート配信のためViteの`base`設定は不要である。募集期間中の一般公開は規約で禁止されるため、Cloudflare Accessのメール宛て一度きり暗証番号認証で閲覧者を限定する。締切から入賞発表までの凍結を守るため、提出時のコミットにタグを付けて固定する。

## 6. ゲームループと状態管理

描画の繰り返しは、ブラウザの描画の合図（requestAnimationFrame）で駆動する。判定と得点の計算は、端末のフレーム数に依存しないよう、固定の時間刻みで進め、描画は補間する。理由は、毎分175拍の判定とゲージを端末ごとのフレーム数に左右されず一定に保つためである。画面の遷移は、題名画面、ウォームアップ、プレイ、結果、再挑戦の5状態を、自前の状態管理で扱う。理由は、状態が5つと少なく、依存を増やさず読みやすく書けるためである。

## 7. ミクの常在とモーションの抽象層

ミクは舞台構成の一要素として、プレイ本編の開始時から3次元の世界（読み込んだ舞台の土台モデル・水面・演出文字・灯しと同じ描画空間）に常在し、湖の中心の固定点へ置く。位置は本編前に確定する。

モーションは後から付加できるよう、ボーンを操作する層を抽象化する。MVPはポーズを固定し、モーションを与えない実装とするが、抽象の差し替えで次の2方式を扱えるようにする。第1は手続き的なモーションで、`@pixiv/three-vrm` の `VRMHumanoid` の正規化したボーンへコードで回転を与える。第2は再生型のモーションで、`@pixiv/three-vrm-animation` でVRM Animationを読み込み、`createVRMAnimationClip` で動作の区切りを作り、`THREE.AnimationMixer` を `vrm.scene` に対して回して再生する。いずれの方式でも、毎フレームに `vrm.update` を呼んでばねの揺れと表情の更新を進める。モーションの素材源の規約適合は `docs/research/05-asset-procurement.md` に整理し、採否は保留とする。
