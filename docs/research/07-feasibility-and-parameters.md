# 調査詳細：コア機構の成立性と定量パラメータ

本文書は、コア機構が技術的かつ音楽的に成立することの検証結果と、主要パラメータの見積もり値・調整範囲・感度を、確定形で記す。閾値と計算式は、採用した理由を先に述べてから値を示す。検証に使った一次データは、TextAliveの音楽地図のダンプ（`docs/analysis/takeover.songmap.json` と `docs/analysis/takeover-melody.json`）である。

## 1. コア機構の成立性

### 1.1 和音データの被覆率
コードトーン格子は、その瞬間の和音の構成音をY軸に割り当てる。よって和音の情報が楽曲の全域を切れ目なく覆うことが前提になる。TAKEOVERの和音は210個で、0ミリ秒から237269ミリ秒まで切れ目なく連続し、曲の長さ237250ミリ秒の全域を覆う。和音の根音を継続時間で重み付けすると、ファのナチュラルマイナー（相対する長調はラ♭メジャー）が支配的である。よって、コードトーン格子は楽曲の全域で機能する。

和音の名前（`IChord.name`）は「Fm」「DbM7」「Ab/Eb」のような文字列で提供されるため、アプリ側で名前を音高の集合に変換する処理が必要である。

### 1.2 和音が存在しない区間の扱い
旋律の音高のデータ（`takeover-melody.json`）には、和音との一致の判定が「真」「偽」「未定義」の3値で記録されている。未定義は、その時刻に和音が存在しない区間（コード無し、英語の頭文字でN.C.）であり、判定の前提がないことを意味する。これは「和音から外れている」とは異なる。N.C.は楽曲全体の4.1パーセントで、その大半は無音か区間の境界であり、歌唱中の実質的な欠落は32.9秒から34.3秒の1.4秒だけである。

採用理由を先に述べる。境界の短いN.C.は前後の和音と連続するため、直前の和音をそのまま使うのが破綻しにくい。歌唱中の長いN.C.は、楽曲の調（ファのナチュラルマイナー）の音階を使うと曲調に馴染む。よって、既定では直前の和音を保持し、歌唱中の長いN.C.だけ楽曲の調の音階を割り当てる。この区間と方針は曲プロファイルにあらかじめ書き込み、実行時の計算をなくす。

### 1.3 操作音の楽曲との整合
採用理由を先に述べる。市販の楽曲はほぼA音を440ヘルツに合わせて作られているため、音高から周波数への標準の変換式（440×2の((音高番号−69)/12)乗）で楽曲と整合する。密な電子音楽の上に重ねるため、他の音を覆い隠さない音色と帯域が必要である。よって、立ち上がりが短く減衰の速い撥弦・鐘・木琴系の音色を使い、300ヘルツより低い帯域を削り、1キロヘルツから4キロヘルツの帯域に置く。協和を保つため、和音の構成音に安全な付加音（長調は9度と6度、短調は♭7度と11度）を加えた5音音階を使い、どの音を叩いても協和する。

### 1.4 同時発音の管理
採用理由を先に述べる。基本のタップの頻度は2拍に1回（686ミリ秒に1回）で、サビの倍速でも最短で171ミリ秒に1回であり、Web Audioにとって高い負荷ではない。よって、タップのたびに音源と音量調整の節点を新しく作り、減衰の後に停止し、停止の後に接続を切って記憶を解放する方式で十分である。同時に鳴る音の数の上限を16から24とし、上限に達したら最も古い音を短く消してから止める。

### 1.5 結論
コア機構（タップのY軸を和音の構成音に割り当て、どの位置を叩いても協和し、音程付きの操作音を楽曲に重ねる）は、技術的かつ音楽的に成立する。必須の対応は、和音が存在しない区間のY軸の代替の規則と、操作音を判定から切り離して即座に鳴らす設計の2点である。

## 2. 定量パラメータの見積もり

すべての値は、本文書の見積もりを初期値とし、実装後のプレイ検証で調整する方針である。

### 2.1 フルに可能なタップの総数
採用理由を先に述べる。基本のタップの頻度は2拍に1回である。TAKEOVERの拍は676個のため、2拍に1回では338個になる。サビは3区間で各64拍、合計192拍あり、サビだけ1拍に1回にすると、サビで192個、サビ以外の484拍で242個、合計434個になる。よって、フルに可能なタップの総数の見積もりは434で、調整範囲は340から676である。

### 2.2 タップ総数上限（一回性）
採用理由を先に述べる。全6箇所の見せ場をすべて最適に投下できない密度にすると、配分の戦略が生じる。フルに可能なタップ434に対し6割にすると、平均的なプレイで6箇所の見せ場のうち4箇所程度しか最適に投下できない密度になる。よって、タップ総数上限の点推定は260（フルの6割）で、調整範囲は170から350（4割から8割）である。上限を上げると取り切れて一回性が薄れ、下げると取捨選択が鋭くなるが下げすぎると失敗のない床と矛盾する。

### 2.3 Y軸スロット数
採用理由を先に述べる。和音は3和音が3音、4和音が4音である。これを2オクターブに展開すると、3和音で6音、4和音で8音になる。横持ちの親指の分解能と画面の幅から、叩き分けられるのは5から7である。よって、Y軸スロット数の点推定は7（3和音の6音に根音の重複か安全な付加音を1つ加えた数）で、調整範囲は5から9である。スロットを増やすと音程の表現が細かくなるが、毎分175拍の高速では隣のスロットへの誤りが増える。

### 2.4 判定窓
採用理由を先に述べる。毎分175拍では1拍が343ミリ秒である。一般のリズムゲームの満点の許容幅は前後50ミリ秒前後が標準で、本作は連続値で評価し外しても発音し光点は最小になる。よって、JUSTの中心の前後40ミリ秒（1拍の約12パーセント）を満点とし、前後90ミリ秒（1拍の約26パーセント）まで線形に得点を減らし、それより外は床の得点とする。点推定の判定窓は前後60ミリ秒（1拍の約17パーセント）で、調整範囲は前後40から90ミリ秒である。窓を広げると初心者には易しいが手応えが減り、狭めると手応えは増すが倍速のサビで取りこぼしの不満が出る。タイミングは軌跡上の距離で定義するため、この時間の窓は各ノーツ点でカメラの軌跡上の速さを掛けて距離の窓へ翻訳する。詳細は `docs/research/04-ux-and-chart-design.md` に記す。

### 2.5 ゲージと投下
採用理由を先に述べる。満タンのゲージで1回の投下が成立し、かつ全6箇所では取り切れない配分にするため、想定するタップ数と見せ場数から逆算する。タップ総数上限260を見せ場6箇所で割ると、1箇所あたり約43タップになる。よって、満タンのゲージはおよそ50タップで貯まる設計とし、これは投下5回ぶんに相当する。タップ1回あたりの蓄積は、片方の成功で基本量、両方のJUSTでその2倍とする。投下はゲージを消費し、消費した割合と見せ場の重みに応じて得点の倍率を上げる。投下の発動はノーツ効果音の音色も変える。189秒地点の見せ場の重みを最大にする。蓄積を速める、または上限を下げると、投下の頻度が増えて手軽になるが戦略性が下がる。蓄積を遅くする、または上限を上げると、投下が貴重になり、189秒地点へ温存する戦略が立つ。

### 2.6 セクションごとの密度
採用理由を先に述べる。良い譜面は楽曲の構造に密度を対応させる。TAKEOVERは、文字密度の最大が20秒から30秒で毎秒8.3文字、声量の最大が88秒から111秒、密度の谷が110秒から120秒で毎秒0.8文字と200秒から210秒で毎秒0.2文字である。よって、サビは1拍に1回、サビ以外は2拍に1回、密度の谷は休符として投下の踊り場にする。

### 2.7 感度の一覧
各パラメータを上げた場合と下げた場合の特性の変化を示す。

| パラメータ | 上げた場合 | 下げた場合 |
|---|---|---|
| タップ総数上限 | 取り切れて一回性が薄れ配分が作業化する | 取捨選択が鋭くなるが下げすぎると失敗のない床と矛盾する |
| Y軸スロット数 | 音程の表現が細かくなるが命中が難しく誤りが増える | 命中が容易で床が安定するが音程の妙味が減る |
| 判定窓 | 初心者に易しいが手応えが減り得点の差が縮む | 手応えと得点の差が増すが倍速のサビで取りこぼす |
| ゲージの蓄積の速さ | 投下が頻発し爽快だが投下の価値が下がる | 投下が貴重になり戦略性が増すが操作の手持ち無沙汰が増える |

相互の依存は次のとおりである。判定窓と得点は直結し、窓の広さが上手さの差の出る量を決める。タップ総数上限とゲージは連動し、上限が満タンへの到達回数の母数を決める。Y軸スロット数と判定窓は連動し、スロットが多く窓が広いと隣への誤りが急増する。

## 解析先行との関係

本文書のパラメータ（判定窓・タップ総数上限・Y軸スロット数・ゲージ・密度）は、対象楽曲の完全な解析の成果物（曲プロファイル）から導く。よって、解析の成果物が形式検査を通る前に演出と譜面の実装へ進まない（解析先行のゲートは `docs/research/04-ux-and-chart-design.md` と `docs/research/08-quality-assurance.md` に定める）。各パラメータは本文書の見積もりを初期値とし、実装後のプレイ検証で調整する。
