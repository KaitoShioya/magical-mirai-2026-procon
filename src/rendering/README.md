# rendering — 単一WebGL描画領域のビュー

- **責務**: 状態を読んで描く「ビュー」。描画器の統括・Renderer設定・透視投影と正射影のカメラ・合成パイプライン（パス順／性能劣化制御／成果物の書出）・シーン組立（光源・水面・舞台土台）・描画対象クラス群（各 update/dispose）・ローダ。
- **禁止依存**: 判定・得点・時刻の論理を持たない（状態を読むだけ）。`profiles`・`tools` を import しない。物体ごとの表示層（`Object3D.layers`）で合成しない（明示的なパス順を使う）。
- **担当Issue**: マイルストーンM2（成果物の書出は #71、舞台土台モデルは #105）
- **確立済みの土台（Issue #8）**: 単一の WebGLRenderer・透視投影カメラ・指数霧（FogExp2）・画素密度上限2・リサイズ追従。寸法計算は `viewport.ts` の純粋関数（`clampPixelRatio`・`computeAspect`）に切り出して単体検証する。WebGL の配線は `renderRoot.ts`（`createRenderRoot`）、定数は `constants.ts`。後続の反射(#9)・発光点(#10)・ブルーム(#11)・カメラ軌跡(#13)・層合成(#15)はこの土台へ積み上げる。
- **公開契約**: `createRenderRoot(container, options?)` は `render()`・`update(秒)`・`mountCenterCharacter(config)`・`addOverlayObject(object)`・`removeOverlayObject(object)`・`setCameraPose(position, target)`（適用可否を真偽値で返す）・`resize(width, height)`・`state()`・`dispose()` を返す。`options.reflectionResolution`（省略可・既定512）は反射解像度。`addOverlayObject`／`removeOverlayObject` は2次元層（#15）へ表示物を足す・外す（WebGL不可なら何もしない）。`state()` の戻り値（診断・検証用）は `webglAvailable`・`pixelRatio`・`drawingBufferWidth`・`drawingBufferHeight`・`clearColorHex`・`cameraAspect`・`cameraPosition`・`cameraDirection`・`cameraPoseRejectedCount`・`reflectionEnabled`・`reflectionResolution`・`bloom`・`centerFigureStatus`・`centerFigureError`・`overlay`（2次元層の物体数と視錐台、WebGL不可なら null）を持つ素の構造とする。
- **カメラ軌跡の本編結線は #59 が担当**: 評価器（`src/utils/cameraTrajectory.ts`、#13）と `setCameraPose` を使い、曲プロファイルのカメラキーフレームから本編プレイ中のカメラ姿勢を毎フレーム駆動するのは Issue #59（TAKEOVER通しプレイ成立）が行う。#13 は評価器・`setCameraPose`・受け入れ診断（暫定キーフレーム）までを担う。
- **取り込み方針**: three.js は必要部品のみを名前付きで取り込む（`import { Scene, Color, FogExp2, PerspectiveCamera, WebGLRenderer, Vector2 } from "three"`）。容量を抑えるため、まとめ取り込み（名前空間取り込み）やデフォルト取り込みは使わない（`docs/research/06-tech-stack-and-architecture.md` §5）。
- **平面反射（Issue #9）**: 深夜の暗い湖面を平面反射方式（水面を鏡とみなし鏡像位置のカメラで世界をもう一度描く方式）で描く。反射水面は `water.ts`（`createWater`、`three/examples/jsm/objects/Reflector.js` の `Reflector` を使用、無効時は不透明な `Mesh`）。反射確認用の暫定発光点は `placeholderGlow.ts`（決定的・非対称の固定配置。発光点本実装 Issue #10 で置換する暫定物）。起動時パラメータ `refl` の解釈は純粋関数 `reflection.ts`（`resolveReflectionResolution`）。定数は `constants.ts`（`WATER_PLANE_SIZE`・`WATER_COLOR`・`DEFAULT_REFLECTION_RESOLUTION`・`REFLECTION_RESOLUTIONS`）。水面は高さ0に置く。
  - **実装で対処する事項**: 資源解放は反射経路で `Reflector.dispose()`（描画ターゲットとマテリアルのみ解放）に加えジオメトリを解放、無効経路でジオメトリとマテリアルを解放する。反射の描画ターゲット解像度はコンストラクタで固定し表示リサイズに追従しない（反射コストを一定に保つため意図どおり）。実行中の解像度切替は再生成が要るが `refl` は起動時に一度だけ読むため不要（実行中の自動縮退は Issue #97 の範囲）。
  - **実機スクリーンショットで確認する事項**: 色の見え・霧の見え・反射面の占有は、レンダラの出力色空間・トーンマッピング・Reflector のシェーダの組み合わせで変わりうるため、実機画像で確認する。
  - **`refl` 規約**: `refl=0` で無効、`256`・`512` で有効解像度、未指定・空文字・不正値は既定512。本番ビルドでも有効にする（実機での反射の手動調整、自動縮退 Issue #97 導入前の退避手段）。同名パラメータの重複は `URLSearchParams.get` が最初の値を採るため最初の値が使われる。
  - **舞台土台モデル（Issue #105）連携**: 水面のジオメトリは現状 `water.ts` 内で平面として生成する。#105 導入時はこの生成箇所をモデル内の約束した名前のメッシュ（名前を `water` とする）のジオメトリへ差し替える。高さ規約として、舞台土台の水面相当面を水面（高さ0）と同一平面に重ねない、または水際の地形を水面より明確に上へ置くことを #105 に引き継ぐ（同一平面の描画順の揺れを避けるため）。
  - **性能判定の所在と完了条件の境界**: Issue #9 の性能合格は試作 `prototype.html` 基準（解像度1920×1080・画素密度上限2・反射解像度256と512で、平均55フレーム毎秒以上かつ下位5パーセンタイル45フレーム毎秒以上）。判定スクリプトは `scripts/reflection-fps.mjs`（実GPUでのみ合格しうる）。本編アプリへブルーム(#11)・発光点本実装(#10)・雨・カメラ軌跡(#13)を統合した状態での反射性能の再計測、および本編アプリへのフレーム計測フックの追加は Issue #97 で行う。
  - **暫定物の置換先**: 暫定発光点は Issue #10、暫定カメラ視点（`renderRoot.ts` の局所定数。水面より上に固定。カメラが水面下だと Reflector は反射を描かない）は Issue #13。反射に含める対象と除外する対象の方針のうち、2次元層を反射に含めないことは #15 が確定済み（下記）。ミクを反射に含めるか否かは #92 で扱う。
- **層合成（Issue #15、実装済み）**: 単一の WebGL 描画領域で、3次元の合成の後に2次元層を最前面へ重ねる。`overlay.ts`（`createOverlayLayer`）が正射影カメラ（`OrthographicCamera`）と専用 `Scene` と物体登録口を持つ。
  - **合成手順**: 描画器の `autoClear` を構築時に偽へ固定し、`render()` で「3次元世界を合成器（`bloomComposer`）で描く → `setRenderTarget(null)` で出力先を画面へ明示 → `clearDepth()` で深度のみ消す → 正射影カメラで2次元層を描く」の順に行う。合成器が無い防御経路では3次元描画の前に自前の `renderer.clear()` で色と深度を消す。手順2〜4は `overlay.composite(renderer)` に集約し、本番の `renderRoot.render()` と受け入れ診断ページが同じ関数を呼ぶ。物体ごとの表示層（`Object3D.layers`）は使わず、明示的なパス順で合成する（`docs/decisions/architecture.md` §3.4）。
  - **座標規約**: 画面の高さを単一の基準軸として両軸を同一単位で正規化する。中央原点・高さ方向 +1〜-1（正規化デバイス座標と一致）・幅方向 -縦横比〜+縦横比（縦横比 = 幅÷高さ）。両軸の単位長が等しく等方（丸い形が真円）。可視範囲は幅と高さの比だけで決まり解像度にも画素密度倍率にも依存しない。視錐台は純粋関数 `computeOverlayFrustum`（`viewport.ts`）で求め単体検証する。入力層の正規化座標（左上原点・下方向正・0〜1）から2次元層の座標への写像は純粋関数 `overlayPointFromNormalized`（`viewport.ts`、`x=(nx-0.5)×2×縦横比`、`y=(0.5-ny)×2`）。座標規約の単位から端末画素への換算係数は両軸とも「描画バッファ高さ÷2」。
  - **2次元層内の物体の重ね順**: 2次元層に載る物体どうしの前後は本Issueの範囲外。後続Issue（落下式レーン #57・音程帯 #58）が描画順（`renderOrder`）の分離または深度判定・深度書き込みの無効化（`depthTest`・`depthWrite` を偽）で扱う。
  - **反射・ブルームに含めない**: 2次元層は3次元シーンとは別の `Scene` に置き、合成の後に正射影カメラで描くため、反射水面（`Reflector`）が描く世界にも合成器のブルーム対象にも含まれない（2次元層は水面に映り込まずブルームでにじまない）。
  - **資源の所有**: 2次元層へ載せた物体のジオメトリ・マテリアル・テクスチャは載せた側が所有して解放する。`overlay.dispose()` はシーンからの取り外しのみを行い、載せた物体の `dispose` は呼ばない。
  - **検証**: 視錐台と座標写像の決定的検証は単体テスト（`viewport.test.ts`）。合成手順の実機検証は受け入れ診断ページ `layer-composite.html`（`src/rendering/diagnostics/layerComposite/main.ts`）で、本番と同じ合成器経路で数フレーム描いた画面の画素を生の `gl.readPixels` で読み戻し、最前面（中央が赤）・z-fightなし（覆う領域の全標本が赤）・3次元の色の保持（外側が緑）を `window.__layerCompositeState` で公開する。`scripts/rendering-layer-smoke.mjs` が検査する。本番の `renderRoot` が2次元層を組み込み視錐台が規約どおりであることは `scripts/rendering-smoke.mjs` が確認する。診断ページは本番ビルド（`--mode app`）では配信しない。
- **性能バジェット自動劣化制御（Issue #18）**: 実行中にFPSを監視し、目標60フレーム毎秒を維持するよう画素密度倍率（DPR）とブルームを段階的に下げ、回復したら戻す。本番でも常時動く実行時機能で、設計の出典は `docs/decisions/architecture.md` §3.8（縮退順序＝画素密度→後処理、ヒステリシスと時間窓で判断）。
  - **責務の分離**: FPSから劣化段階を決める判定は純粋モジュール `performanceBudget.ts`（three.js非依存・`viewport.ts` と同じ方針で単体検証する）。段階を実際に描画へ適用するのは `renderRoot.ts` の `applyPerformanceLevel`。段階ごとの描画設定の数値（DPR上限・ブルーム解像度倍率・ブルーム有効）とFPS閾値は `constants.ts`（性能閾値の所有は `src/config/tuning.ts` が #18 と定める）。
  - **段階ラダー**: 4段階。段階0=DPR上限2・ブルーム0.5、段階1=DPR上限1.0・ブルーム0.5、段階2=DPR上限1.0・ブルーム0.25、段階3=DPR上限1.0・ブルーム無効。段階間の差を一つの操作だけにして各遷移の描画バッファ再確保を最小化する。閾値は目標60・下降55・復帰58（不感帯3）、時間窓2秒、滞留は下降3秒・復帰8秒（非対称で再劣化の往復を抑える）。値の採用理由は各定数のコメントに先述する。
  - **対象外**: 反射解像度の実行時縮退は含めない（起動時 `refl` のままで、実行時の反射縮退は Issue #97 へ委譲）。理由は反射の実行時変更が `water` 再生成を伴い「低下が滑らか」と緊張するため。描画物体の間引き（§3.8の第3段）も対象外。
  - **実行時API**: `bloom.ts` に `setResolutionScale`・`setEnabled`（いずれも変化有無を返す）を追加。`renderRoot.ts` の `applyPerformanceLevel` は要求段階が現在と同じなら何もせず、固定順（DPR上限→ブルーム解像度→ブルーム有効）で適用し、何が実際に変わったか（DPR・ブルーム解像度・ブルーム有効・いずれか）を返す。`RenderState` に `degradationLevel` と `drawCalls` を加える。
  - **描画命令数の計測**: `renderer.info.autoReset` を偽にし `render` の先頭で一度だけ `renderer.info.reset()` を呼ぶ。これでブルーム合成の各パスと2次元層を合算した1フレームの描画命令数を `drawCalls` で読める（指標「描画命令<100」）。
  - **アプリ結線**: 統括（`src/app/index.ts`）が毎フレーム `recordFrame` に実経過を渡し、段階変化時だけ `applyPerformanceLevel` を呼び、実効変化の有無を `notifyApplied` で返す（端末画素密度倍率が1以下で段階0→1が無変化のときに次の下降を短縮する）。タブ復帰（`onResume`）で `reset` する。FPSの読み出し口（`window.__fps`・`__avgFps`・`__fpsSamples`・`__resetFps`・`__drawCalls`・`__perfLevel`・`__perfLevelHistory`）は診断モード（`?smoke=1`）でのみ公開し、適応そのものは本番でも動く。
  - **検証**: 判定の決定的検証は単体テスト `performanceBudget.test.ts`（下降・段階進行・復帰・不感帯で不変・滞留遵守・実効変化なしの短縮・過大経過の頭打ち・reset）。描画器が段階を実際に適用することは受け入れ診断ページ `perf-budget.html`（`src/rendering/diagnostics/perfBudget/main.ts`）が段階0〜3を適用し `window.__perfApplied` で公開し、`scripts/rendering-perf-smoke.mjs` が画素密度倍率の低下・ブルーム解像度0.25・ブルーム無効と最終出力パス維持・描画命令数100未満・各遷移でちょうど1つのレバーだけが変わること（再確保の最小化＝低下が滑らか）を検査する。同ページは `?view=1` で目視確認用の閲覧モードになり、湖のシーンを連続描画してキーボードの0〜3で段階を切り替え、各段階の画素密度の精細さ・ブルームのにじみ・ブルーム無効時の色味の保持を目視で比較できる。本編アプリ経路（`?smoke=1`）の描画命令数が100未満で劣化段階が配線されていることは `scripts/rendering-smoke.mjs` が確認する。段階適用直後の1フレーム所要時間は、段階適用が過度に重い処理になる回帰の検出として上限200ミリ秒（実測最大の数十倍。性能の合否ではない）を超えないことを確かめる。「低下が滑らか」は「1段階で1レバーだけ変化」と「判定器が振動せず滞留で切替を稀に保つ」ことで担保する。診断ページは本番ビルド（`--mode app`）では配信しない。実機での平均55以上の確認・VRM常在を含む描画命令数の計測・正式な性能ゲートは Issue #19・#97 が担い、本Issueでは二重化しない。
- **テスト方針**: 寸法計算と反射解像度の解釈という純粋関数は Vitest（node環境）で単体検証する（`viewport.test.ts`・`reflection.test.ts`）。WebGL を生成する配線は node 環境で生成できないため、実ブラウザの Playwright スモーク（`scripts/rendering-smoke.mjs`、反射の有効・解像度の診断を含む）で検証する。反射の性能は実GPUの性能ゲート（`scripts/reflection-fps.mjs`）で判定し、鏡像反転と映り込みは同ゲートが保存する画像（`scripts/.quality-out`、バージョン管理から除外済み）で手動目視する。
- **カメラ軌跡の診断ページ（#13、`diagnostics/cameraTrajectory/`）**: 2種類ある。
  - 受け入れ診断 `camera-trajectory.html`（`main.ts`）: 暫定キーフレームで全曲長を掃引し、滑らか追従・最小速度・適用拒否0・終点一致の指標を `window.__cameraTrajectory` で公開する。`scripts/camera-trajectory-smoke.mjs` が検査し、検証ビルド（`vite.config.ts` の入力）に含む（本番ビルド `--mode app` では非配信）。
  - 目視確認 `camera-trajectory-view.html`（`view.ts`）: 俯瞰視点で軌跡曲線・キーフレーム点・床格子・カメラ位置と注視点と視線方向を描き、評価器の `poseAt` 出力に沿って動かす可視化ツール。**開発サーバ（`npm run dev`）専用**で、ビルド入力・本番配信・スモークには含めない。クエリ `seconds` で1周の再生秒数を変える。
- **WebGL不可時の縮退**: WebGL の描画文脈を生成できない端末では `createRenderRoot` は WebGLRenderer を呼ぶ前に `isWebGL2Available` で判定して縮退し、`webglAvailable` を偽にし描画を無効化する。エンジン・画面・操作は動き続ける。
- **夜の照明・中心オブジェクト・VRMローダ（Issue #64）**: 湖の中心に常在する初音ミクを描く。
  - **照明**: `lighting.ts`（`createNightLighting`）。淡い環境光（`AmbientLight`）と背後上方からのリムライト（`DirectionalLight`）の2灯を `Group` で返す。標準マテリアルのモデルを深夜の背景から分離する。水面（Reflector）と発光点（光源非依存の `MeshBasicMaterial`）は影響を受けない。影は本Issueでは扱わない。
  - **中心オブジェクト**: `entities/centerFigure.ts`（`createCenterFigure`）。初期はコード描画の光柱（縮退表示）を中心へ立て、VRM読み込み成功で光柱からVRMへ差し替える（`swapToVrm`）。契約は `object3d`・`update(秒)`・`status()`・`dispose()`。
  - **VRMローダ**: `loaders/vrmLoader.ts`（`loadVrm`）。`GLTFLoader` に `VRMLoaderPlugin` を登録して読み込み、頂点と骨を整理（`VRMUtils.removeUnnecessaryVertices`・`combineSkeletons`）、視錐台カリングを無効化、VRM0.0系は前方を正規化（`VRMUtils.rotateVRM0`）。後始末は各テクスチャの画像ビットマップ（ImageBitmap）を閉じてから `VRMUtils.deepDispose` でGPU資源を解放する（`docs/decisions/architecture.md` §3.5）。
  - **公開契約の追加**: `RenderRoot` に `update(秒)` と `mountCenterCharacter(config)` を持つ。`update` は中心オブジェクトを毎フレーム進め、統括が `render` の前に呼ぶ。`mountCenterCharacter` はVRMを読み込んで差し替え、成功で `true`・失敗で `false` を返す。複数回呼んでも最後の呼び出しの結果だけを採り（世代管理）、後始末との競合では後から届く読み込みを取り込まず解放する。
  - **設定と差し替え**: モデルの配信先・配置・スケール・向き・出典・来歴は `src/config/character.ts`（`MIKU_CHARACTER`、型は `src/types/character.ts`）に集約する。差し替えは設定値の変更と `public/models/miku/` のファイル置換だけで完結する。
  - **診断状態**: `state()` の `centerFigureStatus`（`fallback`＝光柱・`loaded`＝VRM・`error`＝読み込み失敗で光柱継続）と `centerFigureError`（失敗の短い理由）で、表示と縮退をスモークが判定できる。
  - **出典の常時表示**: ピアプロ・キャラクター・ライセンスの指定文言は、読み込みの成否に依らずアプリ起動時から常時表示する（DOMバッジは `src/app/attribution.ts`）。包括的なクレジット区画は #77・#82 が統合する。
- 将来の内部構成: 描画器統括 / Renderer / cameras / pipeline / scene / entities / loaders。詳細は `docs/decisions/architecture.md`。
